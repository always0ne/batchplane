[English](./product-scope-and-editions.md)

상태: 2026-10-05 제품 방향과 작업 범위를 정합화했다.
구현 순서는 [승인된 로드맵](./control-plane-migration-plan.ko.md), 준비 상태는
[요구사항 추적표](./requirements-traceability.ko.md)를 참조한다.

## 제품 정의

BatchPlane은 통합 배치 통제·감사 플랫폼이다. 여러 배치 엔진의 통합이 핵심
목적이다. 승인, 필수 Gate 강제, 내부 권한 관리, 운영 이력과 실패 검토 역시
P0 요구이며 선택 부가 기능이 아니다.

native 플랫폼은 스케줄링·runner·실행을 소유한다. BatchPlane은 공통 요청·승인·
권한·통제된 변경·실행 허용·기록 연결·운영 조회·감사를 소유한다. GitHub Actions를
먼저, Jenkins를 다음으로 지원하고, 세 번째 플랫폼은 선정 후 실제 검증한다.
SCDF는 예시였으며 확정된 세 번째 플랫폼이 아니다.

## 공통 제품 의미

Workspace는 접근·정책 경계다. 플랫폼 연결은 그 안에 구성된 엔진 설치 또는
엔드포인트를 식별한다. 두 개념은 동의어가 아니다. 배치는 제품 식별자와 플랫폼별
외부 참조를 가진다.

변경 요청서는 정확한 제안 형상을 승인한다. 수동 실행 요청서는 정확한 대상과
입력을 승인한다. native 스케줄 회차는 새 사람 승인 없이 소유 배치·스케줄의
승인된 형상을 사용한다.

통합 요청서 하나에 여러 배치·작업 유형·Workspace를 담을 수 있다. 생성 전에
모든 대상의 공통 승인자가 있어야 하며 한 공통 승인자가 전체를 승인한다.
UI가 모아 보여줘도 저장소별 신뢰 경계는 사라지지 않는다. Lite의 저장소 간
증적·자격 증명 설계는 #142 승인이 더 필요하다. 어렵다는 이유로 합의된 사용자
흐름을 조용히 축소하지 않는다.

승인, 전달 수락, Gate 허용, 업무 완료는 서로 다른 사실이다. 전달 실패가
확인되면 기존 승인을 재사용하지 않고 새 요청이 필요하다. 철회·실제 취소는
native 실행 상태에 따른다. 결과 동기화는 실행을 시작하거나 중단하지 않고
관찰 상태만 갱신한다.

## 감사의 한계

Main은 지원 API에서 결정을 추가 기록하는 방식을 목표로 하며 배포 환경의 접근·
보존 통제가 뒷받침해야 한다. Lite는 구조화된 GitHub 증적을 기록하지만 내용은
GitHub 권한·편집·삭제·보존 정책의 영향을 받는다. digest나 Issue label 자체는
인가 자격 증명도 불변 감사 저장소도 아니다. 삭제된 배치의 과거 형상과 실행
링크에 접근할 수 있어야 하며 native 증거가 없으면 그 사실을 표시해야 한다.

## 전달 범위와 제외 사항

P0가 모든 플랫폼을 한 릴리스에 제공한다는 뜻은 아니다. 플랫폼별 지원 범위를
명시해야 하며 전달 성공 하나로 전체 통제를 증명할 수 없다. Jenkins 초기 첫
흐름 검증과 전체 지원은 구분한다.

소스는 [모듈형 모노레포](./adr/0001-modular-monorepo.ko.md)를 유지하고 런타임
배포물은 분리한다. 새 엔진, 가상의 plugin loader, 두 번째 UI, 호환 프레임워크,
자동 재시도·백필은 승인하지 않았다.

기존 발견·편입, 내보내기, 외부 알림, 재발 보고 요구는 원래 ID와 우선순위를
유지한다. 새 확정 로드맵에 명시적으로 배치되지 않아 상세 범위·시점의 사용자
확인이 필요하다. 제거·선택 기능화하거나 구현됐다고 주장하지 않는다. 정확한
Main 계약과 플랫폼 연동 상세는 해당 로드맵 단계에서 설계한다.
