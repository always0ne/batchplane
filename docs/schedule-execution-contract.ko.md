# 스케줄 실행 계약

[English](./schedule-execution-contract.md)

R4는 승인된 배치 형상으로 무인 스케줄 실행을 인가한다. 이 계약은 GitHub Lite
구현과 플랫폼 중립 UI 의미를 다룬다. 별도 스케줄러·DB·증적 브랜치를 도입하지 않는다.

## 실행 경로

```text
승인된 배치 형상 (스케줄 포함)
  -> native GitHub schedule Run
  -> 요청 기록과 Gate 결정
  -> 업무 진입 시 현재 권한과 원본 attempt 검증
  -> 승인된 SHA checkout과 배치 명령
  -> 해당 스케줄의 job·attempt 결과 증적
```

실행 Issue는 회차를 기록하며 원래 변경 요청 PR이 승인 근거로 남는다. 회차마다
`SCHEDULE_DELEGATED` 승인을 만들지 않고 스케줄 요청을 다른 Run으로 전달하지도
않는다. 수동 요청·승인·dispatcher 동작은 별도로 유지한다.

새 스케줄 payload는 `spec.contractVersion: NATIVE_SCHEDULE_V2`를 사용하며
수동 `expiresAt`과 추론한 `scheduledAt`은 넣지 않는다. 회차 요청 ID는 잘린
식별자가 아닌 정규 튜플의 전체 SHA-256 digest를 사용한다. Gate와 결과 기록 모두
정확한 대상 Issue와 정규 payload를 검증한다. 일치하는 요청 ID나 전달받은 Issue
번호만으로는 부족하다.

Gate는 기존 승인 배치 형상 검증기를 재사용한다. 활성 배치, 활성 스케줄,
workflow 경로/출처, 실제 이벤트, cron 매핑, 승인 산출물 digest가 일치해야 한다.
`SCHEDULE`이라는 텍스트, bot 작성자, Issue, 복사한 댓글은 권한 증명이 아니다.
부분 재실행에서 앞선 Gate 성공 output이 남아 있더라도 업무 진입 시 명령 전에
관련 원본/attempt와 현재 권한을 다시 검사한다. checkout은 이동하는 브랜치가
아닌 검증된 형상 SHA를 사용한다.

통제·결과 기록 job은 Issue 쓰기 권한을 가질 수 있다. 업무 job에는 검증·checkout에
필요한 읽기만 주며 배치 명령에 Issue 쓰기 권한을 부여하지 않는다.

## 식별자와 시간

어댑터는 다음 정규 튜플에서 회차 식별자를 도출한다.

```text
(repositoryId, batchId, scheduleId, sourceRunId)
```

실제 run attempt와 job 식별자는 증적에 함께 기록하지만 새 회차를 만들지는 않는다.
원본 지연은 식별자를 바꾸지 않는다. 하나의 native Run에 여러 스케줄 실행이
포함될 수 있으며 각각 고유 제품 실행 식별자와 정확한 상세·로그 목적지를 가진다.

플랫폼이 신뢰할 수 있는 원본 값을 제공하지 않으면 예정 수행 시각은 알 수 없다.
worker 시각, Run 생성 시각, 가장 최근 cron 시각으로 대체하지 않는다. GitHub는
스케줄을 지연·누락할 수 있다. Lite는 임의 지연 만료, 자동 몰아 실행, 자동 업무
재시도를 추가하지 않는다.

같은 native Run의 전체·부분 재실행은 거부한다. 별도 native Run은 서로 다른
원본 회차다. Lite는 이들 사이의 같은 cron 예정 회차에 대해 exactly-once 처리를
주장하지 않는다. Issue 검색 후 생성은 원자적인 유일성 확보가 아니며 workflow
concurrency도 영속 사용 증거가 아니다. 허용 경계는 스케줄 회차당 하나의 승인된
통제·업무 경로와 GitHub의 정상 job 실행 모델에 의존한다.

## Native 시간대

생성 workflow 항목은 cron과 IANA 시간대를 유지한다.

```yaml
on:
  schedule:
    - cron: "0 5 * * *"
      timezone: "America/New_York"
```

겨울·여름용 UTC 대안을 둘 다 연중 실행되도록 생성하지 않는다. 하나의 생성 배치
workflow 안에서 cron이 같고 시간대가 다르면 검증 오류다. 문서화된
`github.event.schedule`은 트리거한 시간대 항목이 아니라 cron 문자열을 식별하기
때문이다. cron·시간대가 같아도 스케줄 ID가 다르면 별도 업무 경로로 유지한다.
유효하지 않은 조합은 요청 승인 전에 보여야 한다.

이 계약은 문서화된 GitHub.com 동작을 대상으로 하며 모든 GitHub Enterprise
Server 버전을 대상으로 하지 않는다. native 지원 자체가 특정 저장소에서 cron
이벤트를 전달했다는 증거는 아니다.
[GitHub 스케줄 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)와
[native 시간대 발표](https://github.blog/changelog/2026-03-19-github-actions-late-march-2026-updates/)를 참조한다.

## 증적과 실패

필수 요청·허용 증적 쓰기는 업무 허용 전에 성공 응답을 받아야 한다. 응답이
불확실하면 차단하며 POST를 무작정 반복하거나 새 인가를 발급하지 않는다. 업무가
이미 수행됐을 수 있다면 결과 쓰기 실패로 업무를 다시 시작하거나 원래 허용을
초기화하지 않는다.

결과 조회 모델은 해당 스케줄의 정확한 job ID와 attempt를 사용한다. workflow 전체
결론이나 다른 스케줄의 Gate가 그 결과를 대체할 수 없다. 앞선 Gate 허용이 이후
업무 진입 차단을 숨기면 안 된다. 생성 job 식별자와 Gate 기록은 요청·digest·배치·
스케줄을 결합해야 한다. 편집 가능한 결과 댓글이 다른 job으로 독자를 돌릴 수
없어야 한다. 허용 후 명령이 끝난 사실은 이후 변경 요청으로 배치가 비활성화·교체되어도
과거 사실로 남는다. 결과 기록은 새 실행 권한을 부여하지 않는다.
누락·조회 불가·상충하는 증거는 미확인으로 남기며 업무 실패·성공·사람 승인 대기를
꾸며내지 않는다.

`always()` 결과 기록기 자체가 취소되거나 접근 권한을 잃을 수 있다. 최초 Issue조차
기록하지 못했다면 영속 제품 기록이 존재한다고 주장하지 않는다. 확인 가능한 native
Run/로그 증거는 여전히 의미가 있지만 플랫폼 보존 정책의 영향을 받는다. 댓글·label은
편집 가능한 기록이지 불변 원장이 아니다. 조회기는 실제 플랫폼 증거와의 연결을
검증해야 한다. 연결되지 않은 원본 Run도 읽기 전용으로 볼 수 있다. 이를 첫 스케줄에
귀속하거나 workflow 전체 결론으로 업무 실패 처리하거나 요청·담당자를 만들어 붙이지 않는다.

이전 전결 기록은 이력으로 남을 수 있지만 새 실행을 허용할 수 없다. R4는 과거
실행 호환·이전 프레임워크를 추가하지 않는다. 승인 없이 테스트 저장소를 초기화·수정하지 않는다.

## 연결된 UI

공유 UI는 Issue body나 원시 GitHub 식별자를 정책으로 사용하지 않고 제품 클라이언트의
조회 모델을 사용한다. 필수 의미는 다음과 같다.

| 화면               | 필수 동작                                                                                            |
| ------------------ | ---------------------------------------------------------------------------------------------------- |
| 승인함·승인 건수   | 스케줄 회차는 사람 승인 작업이 되지 않는다. 확인되지 않은 권한 근거를 수동 승인으로 우회하지 않는다. |
| Workspace 요청     | 목록에 스케줄 회차를 유지하고 수동 요청과 트리거 유형을 구분한다.                                    |
| 요청 상세          | 스케줄·원본 통제 형상·Gate·실제 실행을 구분한다. 목록이 아니라 해당 실행 상세로 연결한다.            |
| 실행내역·최근 실행 | native 스케줄을 포함하고 서로 다른 스케줄/attempt 연결을 유지한다.                                   |
| 실행 상세·로그     | 회차의 job과 일치해야 하며 업무 명령 우선 로그와 삭제된 배치 이력을 유지한다.                        |
| 실패내역·내처리함  | 업무 실패·Gate 차단·증거 확인 불가를 구분하고 기존 소명·관리자 검토 흐름을 유지한다.                 |
| 감사               | 회차별 사람 승인을 만들지 않고 원본 변경 권한 근거·관찰 회차·Gate·실제 결과를 연결한다.              |
| 변경 차단          | 스케줄 기록을 처리 가능한 수동 승인으로 남겨 향후 변경을 영구 차단하면 안 된다.                      |

스케줄 실패의 최초 담당자는 실행된 승인 배치 형상의 담당자다. bot 요청자나 현재
배치 담당자가 아니다. 등록/변경에서 담당자가 비어 있으면 미리보기·승인 전에 인증된
변경 요청자로 채운다. 폼·diff·digest·저장 형상이 일치해야 한다. 입력된 담당자와
과거 후속처리 배정을 보존한다. 담당자 지정은 Workspace·승인·검토 권한을 주지 않는다.
자유 입력 담당자 검증과 계정 선택기는 별도 개선이며 숨은 대체 배정이 아니다.

## 검증 경계

결정적인 테스트는 정상·비활성·삭제·변경·위조 권한 근거, 과거 output을 가진 전체·부분
재실행, Run 간 재사용, 지연된 식별, 불확실한 쓰기, 여러 스케줄의 혼합 결과,
수동 정책 회귀, native 시간대 검증, 담당자/기본값, 공통 조회 모델을 다뤄야 한다.
변경한 모든 Action 번들은 Node 24 직접 실행과 소스 일치를 확인한다. 영향 UI는
#119를 기준으로 5173 포트에서 영어/한국어, 데스크톱/390px를 검사한다. 전체 R5 UI
구조 이전을 의미하지는 않는다.

실환경 증명은 별도이며 승인된 테스트 Workspace가 필요하다.

1. 제품 변경 머지 후 활성 스케줄과 무해하고 관찰 가능한 명령을 포함한 배치 변경
   요청을 만든다. 재생성 workflow를 검토·승인하며 이미 승인된 파일을 직접 덮어쓰지 않는다.
2. 실제 native 스케줄 이벤트를 기다린다. Run 이벤트·회차 요청·승인 형상·Gate·같은
   Run의 명령·기록된 결과를 확인한다.
3. 회차별 승인이나 두 번째 전달 Run이 없고 제품 요청·실행·실패·감사 링크가
   일치하는지 확인한다.
4. 승인받은 경우에만 별개의 최초 native Run 두 개로 전체 재실행과 실패 업무 job만
   재실행을 검사한다. 후자는 승인된 테스트 정의에 무해하고 의도적으로 실패하는
   명령을 사용한다. 명령이 새로 수행되지 않으며 현재 attempt 차단이 이전 허용을
   상속하지 않는지 확인한다.
5. 실제 시간대·이벤트·attempt 증거는 로컬 fixture와 별도로 기록한다. native 이벤트의
   지연·부재는 로컬 YAML 테스트 실패나 Gate 실행의 증거가 아니다.

결과 동기화(엔진 조회·이력 보정)와 사유 필수 취소(실제 엔진 취소 요청)는 독립적인
향후 동작이다. 로컬 상태를 종결인 것처럼 바꾸거나 업무를 다시 시작해 구현하지 않는다.
지연 모니터링과 백필도 별개다.

2026-10-05 로드맵은 승인 후 철회·실제 취소를 Lite 수용 전 #225에 배치했다.
결과 동기화는 Main 첫 운영 흐름(#228)에 속하며 Lite 추가 결과 보정 시점은 별도다.
Main 지연 모니터링은 #229다. 백필은 추후 논의가 필요하며 이 명령들에 암묵적으로
포함되지 않는다. 준비 상태와 실제 테스트 결과의 구분은 [사용자 QA](./user-qa.ko.md)를 참조한다.
