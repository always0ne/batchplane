# 통합 요청서 기능 명세

[English](./unified-request-feature-spec.md)

## 상태와 제공 경계

#142의 제품 방향을 2026-10-05 갱신했다. R7은 완료했지만 이 기능은 미구현이며
상세 UX·처리 규칙·계약의 승인이 필요하다. Lite 우선으로 제공한다. 입증된 Lite
제약과 사용자 수용이 있을 때만 Main 첫 운영 흐름 직후 첫 후속 과제로 유예하고
초기 Jenkins 검증과 순서를 조율할 수 있다.

현재 변경 요청과 실행 요청 흐름은 독립적이다. 사이트맵 리팩터링 동안 작성·상세
URL, query mode, 승인 규칙, 증적, 명령을 유지한다. 기존 Workspace 요청 목록이
통합 요청서 구현의 증거는 아니다.

## 합의된 요구사항

| ID    | 요구사항                                                                                                                                                                             |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| UR-01 | 요청서는 여러 배치의 항목을 담을 수 있는 제품 수준의 작업 문서다.                                                                                                                    |
| UR-02 | 등록·변경·삭제·실행은 항목 유형이며 서로 다른 유형을 같은 요청서에 담을 수 있다.                                                                                                     |
| UR-03 | 개별 항목이 아니라 요청서 전체를 승인·반려한다.                                                                                                                                      |
| UR-04 | 요청서의 승인 상태와 각 항목의 처리 결과를 구분한다.                                                                                                                                 |
| UR-05 | query parameter로 문서 전체를 단일 작업으로 선택하는 대신 전용 요청서 작성 Page를 제공한다.                                                                                          |
| UR-06 | Lite/Main은 제품 UI 의미를 공유한다. GitHub Issue/PR 표현은 어댑터 책임이며 제품 요청서의 정체성이 아니다.                                                                           |
| UR-07 | 요청자에게 필요한 작업 권한이 있는 여러 Workspace를 하나의 요청서에 담을 수 있다. 통합 조회는 선택한 하나뿐 아니라 권한 있는 Workspace를 포함한다.                                   |
| UR-08 | 포함된 모든 대상 작업의 권한을 가진 공통 승인자가 최소 한 명 있어야 한다. 없으면 생성을 차단한다. 공통 승인자 한 명이 전체를 한 번에 승인하며 Workspace별 독립 승인을 모으지 않는다. |
| UR-09 | 승인·실행 결과·감사 전반에서 항목의 Workspace·연결·배치·작업 식별자를 명시적으로 유지한다.                                                                                           |
| UR-10 | 철회·취소는 미전달·대기·실행 중·종결 항목을 구분한다. 혼합 결과에서 작업이 계속 실행 중인데 전체 철회로 표시하지 않는다.                                                             |

예를 들어 한 요청서에서 배치 A 변경, 배치 B 등록, 배치 C 실행을 요청할 수 있다.
승인은 제출된 요청서 전체를 대상으로 한다. 이 예시가 실행 순서, 원자적 반영,
롤백, 실패 복구를 결정하지는 않는다.

## 목표 화면과 경로

| 화면        | 목표 경로              | 경계                                                    |
| ----------- | ---------------------- | ------------------------------------------------------- |
| 요청 목록   | `/requests`            | 기존 목록. 이 기능 구현 시 통합 모델에 맞춘다.          |
| 요청서 작성 | `/requests/new`        | 향후 전용 Page. 표시명은 Request writing / 요청서 작성. |
| 요청 상세   | `/requests/:requestId` | 향후 제품 요청서 상세·승인·항목별 결과.                 |

작성 경로는 `new`로 합의했다. 앞선 `compose`, `create` 제안은 폐기했다. 이번
리팩터링은 새 요청 경로 두 개를 등록하지 않는다. 컴포넌트 파일명과 전체 화면
배치도 후속 기능 설계에 속한다.

작성 Page는 문서 전체가 등록·변경·삭제·실행 모드인 구조가 아니라 항목들을 담은
요청서를 표현해야 한다. 상세 필드, 항목 편집, 검증 메시지, 검토 표현, 이동 흐름을
함께 정의한 뒤 구현한다.

## 구현 전 결정할 사항

- 같은 배치에서 허용할 작업 조합과 항목 간 의존을 표시·처리하는 방식.
- 항목 순서·부분 성공·실패가 전체 요청에 미치는 영향. 전체 승인이 플랫폼 간
  원자적 트랜잭션을 뜻하지는 않는다.
- 승인 요청 내용과 항목 형상을 이후 처리에 결합하는 방식, 허용된 보정·재제출의
  재승인 방식.
- 현재 등록·실행 통제를 약화하지 않고 Lite가 통합 제품 요청을 Issue·PR 증적과
  연결하는 방식.
- 저장소 간 권한 근거 조회, 공통 승인자 판정, 권한 회수 검사. 이 상세가 이미 합의한
  단일 공통 승인자 모델을 재논의하게 만들지는 않는다.
- 가상의 확장 지점이 아니라 승인 동작에 필요한 제품/클라이언트 계약과 Main 저장 모델.
- 초안·임시 저장 필요 여부. 작성 경로 결정은 둘 중 어느 것도 승인하지 않는다.
- 배치·요청 목록에서 작성·승인·항목 결과·실행 상세·감사까지 이어지는 영어·한국어
  전체 사용자 흐름.

이 목록은 질문이며 기본값이나 구현 작업 목록이 아니다. 리팩터링을 마치면서
초안 저장소·범용 요청 엔진·새 어댑터 API·자동 재시도·롤백·새 승인 정책을 추가하지 않는다.
