# 플랫폼 연동 설계

[English](./platform-provider-contract.md)

상태: 수용된 경계와 Main 설계 예시. 구체 계약은 #227/#228과 #231의 실제 Jenkins
피드백이 필요하다. 2026-10-05 정합화.

## 책임

어댑터는 플랫폼 native 관리·실행·관찰을 제품 작업으로 변환한다. 엔진의 업무
실행 직전 경계에 있는 커넥터가 Gate를 강제한다. 둘은 별도 배포 단위일 수 있지만
선택 플랫폼의 요구를 확인하기 전에 plugin·agent·별도 서비스를 강제하지 않는다.

플랫폼별 DTO·ID·workflow/Job 경로·자격 증명·API 오류는 어댑터 뒤에 둔다.
React는 타입이 있는 제품 데이터와 지원 기능 정보를 받는다.

## 식별자와 지원 기능

Workspace·연결·배치·native 자원 식별자를 구분한다. 여러 연결이 같은 플랫폼
유형이나 Workspace에 속할 수 있다. 플랫폼 키는 엔진 종류를 식별하며 자격 증명이나
권한 역할이 아니다.

실제 지원 작업과 제약을 설명한다.

| 영역        | 필수 설명                                                        |
| ----------- | ---------------------------------------------------------------- |
| 통제된 변경 | 등록·수정·삭제, diff, 낡은 기준 형상 탐지, 확인된 결과           |
| 실행        | 승인 입력 전달, 수락·실패·결과 불명 응답, 정확한 native 식별자   |
| 취소        | 실제 대기·실행 중 취소 명령, 권한, 확인, 이미 종결된 경우의 동작 |
| 스케줄      | native 트리거, cron/시간대 한계, 회차 식별자와 중복 통제 경계    |
| 관찰        | 정확한 attempt, 결과·로그·페이지 처리·결과 동기화·보존           |
| Gate        | 업무 전 강제와 직접·전체/부분 재실행 통제 범위                   |
| 설치        | 필수 배포물·권한·현재 버전·통제된 업그레이드                     |

발견·편입은 이전 요구와 우선순위를 유지한다. 구체 범위와 로드맵 배치는 확인이
필요하다. 이를 삭제하거나 설계 없이 범용 발견 API·설정 스키마 렌더러를 만들라는
허가가 아니다.

## 최소 포트 설계

가상의 기능마다 선택 메서드 인터페이스나 모듈을 만들지 않고 승인된 완결 유스케이스로
포트를 정의한다. Main 첫 GitHub 흐름에는 변경 계획/반영, 통제된 전달, 취소,
관찰/로그, 결과 동기화 책임이 필요하다. 정확한 Kotlin 시그니처와 테이블/API
형식은 미확정이다.

범용 플랫폼 `retry` 작업을 승인된 통제 경로로 노출하지 않는다. 전달 실패가
확인되면 새 요청으로 제품 인가를 새로 받아야 한다. native 재시도 의미가 이
정책을 덮어쓰지 않는다.

## 외부 효과

작업은 제품 연결 정보, 대상 연결, 승인 형상, 플랫폼 작업/attempt 참조를 유지한다.
예상과 다른 기준 형상에 승인 diff를 적용하지 않고 낡은 형상을 거부한다.

플랫폼이 멱등성을 지원하면 실제 계약을 사용한다. 수락 여부가 불명이면 비멱등
전달을 무작정 반복하지 않고 상태를 대조한다. 유일한 MySQL 행이나 Issue label
하나만으로 native 업무 효과의 exactly-once를 보장할 수 없다. 확인된 거절과
불확실한 네트워크·관찰 실패를 따로 보존한다.

## 관찰

실제 지원 기능에 맞게 인증된 이벤트나 플랫폼 조회를 사용한다. 완료를 꾸며내지
않고 결과·진단 데이터를 정규화한다. 같은 attempt의 반복 이벤트는 새 실행을
만들지 않는다. 결과 동기화는 증거를 읽고 제품 관찰 상태를 보정하며 재시도·취소
작업이 아니다.

조회는 최초 페이지 이후에도 범위를 제한해 가져올 수 있어야 한다. 플랫폼 보존
한계와 권한 실패는 일치 이력 없음과 구분한다. 비밀정보가 담긴 진단을 브라우저
telemetry나 감사에 유출하지 않는다.

## 스케줄링

플랫폼이 스케줄을 트리거하며 권한 근거는 승인된 배치·스케줄 형상이다. 설정한
시간대와 실제 native 회차 식별자를 유지한다. 고정 UTC offset으로 대체해 서머타임
의미를 조용히 바꾸지 않는다. 모르는 예정 시각을 worker 시작 시각으로 대체하지 않는다.

플랫폼이 증명하지 못하는 Run 간 예정 회차 유일성을 약속하지 않는다. 자동 백필·
몰아 실행·재실행은 승인하지 않았다. Main 지연 모니터링은 #229이며 현재 Lite
상세는 [스케줄 계약](./schedule-execution-contract.ko.md)에 있다.

## UI와 패키징

제품 Page는 사용자 흐름과 레이아웃을 소유한다. 타입이 있는 플랫폼 설정 컴포넌트는
기존 runtime 경계에 주입할 수 있다. 승인된 필요 없이 신뢰하지 않는 원격 UI 코드,
범용 폼 엔진, 임의 JAR 로더, 별도 SDK를 추가하지 않는다.

구체 연동에 변경이 필요하기 전까지 현재 모노레포 패키지 구조를 유지한다. 플랫폼
계약은 나중에 기여자용 API로 안정화할 수 있지만 이전 descriptor·버전 예시는
출시된 인터페이스가 아니다.

## 검증 순서와 지원 설명

1. 승인 입력, Gate, 결과·로그·감사, 취소, 결과 동기화를 포함한 Main GitHub
   등록·수동 실행을 완결한다.
2. 같은 Workspace의 실제 Jenkins로 같은 흐름을 수행한다.
3. 통제된 변경·삭제, 스케줄, 실패 검토 범위를 확대한다. 의미 있게 특성이 다른
   세 번째 플랫폼을 선정하고 테스트 범위를 승인받는다.

재사용할 플랫폼 정합성 사례는 실제 입력 매핑, 낡은 변경 거부, 권한 검사,
직접·재실행 Gate 강제, 불확실한 수락, 취소, 결과 연결, 시간대 제약, 페이지 처리,
비밀정보 처리를 다뤄야 한다. 다른 위험이 없는데 플랫폼마다 모든 fixture를
복제하지 않는다.

초기 API 연결이나 mock은 전체 플랫폼 지원을 증명하지 않는다. 지원 Job 유형,
강제 한계, 자격 증명, 버전, 실제 증거를 기록한다. 불변 배포물·릴리스·업데이트·
롤백 규칙은 첫 외부 릴리스의 #196이며 개발용 `@main`이 운영 고정 참조라는
뜻이 아니다.
