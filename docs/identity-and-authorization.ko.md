## 소유권

신원 어댑터는 사용자·서비스를 인증하고 외부 사실을 제공한다. BatchPlane은 제품
신원 매핑, Workspace 소속, 인가, 승인 정책과 감사를 소유한다. AD/LDAP/OIDC/
GitHub 그룹과 저장소 권한은 매핑할 사실이며 하드코딩할 제품 권한 정의가 아니다.

이 문서로 Main 신원 제공자, 세션 프로토콜, 전체 역할 목록을 선택하지 않았다.
OIDC, AD/LDAP, GitHub는 배포 요구에 따른 후보들이다.

## Main 코드 전에 승인할 기본 모델

#227에서 다음을 정의해야 한다.

- 안정적인 내부 계정 식별자와 이에 연결되는 외부 인증 신원.
- 플랫폼 연결과 구분되는 Workspace 소속과 권한 범위.
- 사람·자동화·플랫폼 행위자와 기록할 인가 근거.
- 요청·실행·승인·관리·후속 검토·감사 권한.
- 작업별로 대상으로 삼을 수 있는 배치·연결·Workspace.
- 권한 회수/현재 정책의 적용 방식과 과거 역할 증거.
- 통합 요청서 전체 대상의 권한과 실제 취소 권한 매핑.
- 이 개념들을 승인한 뒤 구체화할 API/MySQL 표현.

연결은 한 Workspace에 속한 여러 플랫폼 중 하나일 수 있다. 로그인 세션은
Workspace가 아니다. 전역 관리자가 모든 Workspace 작업까지 승인할 수 있다고
조용히 가정하지 않는다.

## 승인된 요청 규칙

기본값은 자가승인 금지다. Workspace에서 명시적으로 선택하는 모드는 다음과 같다.

| 모드                    | 의미                                                                                |
| ----------------------- | ----------------------------------------------------------------------------------- |
| `SELF_APPROVAL_BLOCKED` | 요청자는 자신의 요청을 승인할 수 없다.                                              |
| `SELF_APPROVAL_ALLOWED` | 다른 승인 자격을 충족하는 승인자는 자가승인할 수 있다. 증적에 이를 표시한다.        |
| `AUTO_APPROVE`          | 대상 요청 유형에는 정책 기반 승인 증적을 부여한다. 허용된 수동 자가승인도 포함한다. |

이 모드들은 자격 없는 사용자에게 승인자 역할을 주지 않는다. 화면 허용 여부,
실제 명령과 Gate는 일치해야 한다. Lite 정합성과 승인 형상 조회 완전성은 #223이다.

대상 배치 변경과 수동 실행은 현재 정책을 사용한다. 제안된 정책·역할·설치 변경이
제안 값으로 자기 자신을 인가하면 안 된다. 결정 행위자, 대상 digest, 정책 맥락과
사유를 보존한다. 반려에는 사유가 필요하며 승인 내용이 바뀌면 기존 승인은 무효다.

모든 모드에서 native 스케줄은 소유 배치의 승인된 형상을 사용한다. 회차마다 사람의
승인을 기다리거나 자동 승인자를 만들어내지 않는다.

실패 소명에는 권한 있는 관리자의 명시적 검토와 독립된 결정·사유가 필요하다.
자가승인 허용 정책은 자격 있는 관리자가 자신의 제출물을 검토하도록 허용할 수
있지만 AUTO_APPROVE가 소명 건을 조용히 종결하지는 않는다.

## 통합 요청서

한 요청서에 여러 배치·작업 유형·Workspace를 담을 수 있다. 생성하려면 포함된
**모든** 작업의 권한을 가진 공통 승인자가 최소 한 명 있어야 한다. 공통 승인자
한 명이 전체를 승인한다. Workspace별 독립 승인을 모으는 방식으로 대체하지 않는다.

작성자는 대상 작업마다 요청 권한이 있어야 하고 통합 조회에는 허용된 범위만
노출한다. Lite의 저장소 간 증적 저장과 Main의 복수 대상 계약은 #142/#227에서
설계한다. 숨은 공용 저장소 토큰이나 새로운 중앙 권한 주체를 가정하지 않는다.

## 철회·취소·결과 동기화

전달 전 승인된 작업은 요청자, 실제 승인자, 대상 실행 권한 보유자가 철회할 수
있다. 명령·전달·Gate 경계에서 다시 검사한다. 버튼을 숨기는 것은 통제가 아니다.

대기·실행 중에는 사유를 포함한 명시적 실제 취소/중단 확인을 사용한다. 제품
역할과 취소 권한의 상세 매핑은 #225/#227 승인이 필요하다. 취소 요청과 실제
결과를 각각 기록한다. 상태 불명은 완료가 아니며 취소는 이미 발생한 효과의
롤백이 아니다.

결과 동기화는 별도의 관찰 상태 보정이다. 이 기능이 전달·재시도·취소 권한까지
부여하면 안 된다.

## 에디션별 신뢰 경계

현재 Lite는 저장소 기반 Workspace, sessionStorage 전용 GitHub 토큰, 저장소
증적·검증된 API 사실을 사용한다. 브라우저가 침해되면 현재 토큰이 노출될 수 있다.
로컬 상태로 유효 승인 정책을 약화할 수는 없다.

Main은 플랫폼 비밀정보를 서버 또는 자격 증명 저장 어댑터 뒤에 둔다. 브라우저에
재사용 가능한 엔진·커넥터 비밀정보를 주지 않는다. 플랫폼 callback 인증과 Gate
신원은 실제 연결·native 식별자를 결합해야 한다. JSON의 ID를 받았다는 사실만으로
진위를 증명할 수 없다.

지원하는 제품 API는 감사 증거를 보존하지만 GitHub 편집자와 DB 관리자는 인프라
신뢰 경계에 남는다. 과거 증거와 현재 권한은 다르다. 오래된 댓글만으로 현재
권한을 추론하지 않는다.

## 검사와 증거

React뿐 아니라 조회·변경·승인·플랫폼 명령·로그·검토·Gate에서 권한을 강제한다.
토큰이나 원시 신원 assertion 대신 안전한 행위자·대상·맥락·사유를 기록한다.
[QA 시트](./user-qa.ko.md)로 허용·거부 경로를 모두 검증한다. 새 신원 프레임워크나
가상의 권한 계층은 여기서 승인하지 않는다.
