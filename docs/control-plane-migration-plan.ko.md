# BatchPlane 개발 로드맵

[English](./control-plane-migration-plan.md)

상태: 승인된 작업 순서. 2026-10-05 PR #192에서 정합화했다.
범위: 제품 방향과 수용 경계이며, 아키텍처 문서의 모든 API, 테이블, 권한,
연동 예제를 구현하도록 승인한 것은 아니다.

## 현재 기준선

정합화 기준은 main 커밋
`35eb868396d85e80a1a7c81297e59a3a19e9ffb8`이다. R1-R7 리팩터링과 이후
머지된 수정은 출발점이며 다시 수행할 작업이 아니다.

Lite에는 공유 제품 Page와 `BatchPlaneClient`, GitHub 어댑터가 소유하는 증적,
등록·변경·삭제 요청, 승인 모드, 수동 실행, native 스케줄 실행, Gate 검사,
실행 로그, 삭제된 배치의 이력, 실패 소명과 명시적 관리자 검토가 이미 있다.
이는 구현 존재 여부이며 모든 흐름의 QA 통과를 선언하는 것이 아니다.
native 스케줄은 여전히 #202에서 실제 GitHub 증거를 확보해야 한다.
알려진 권한·파라미터·생명주기·조회 결함은 아래에 남아 있다.

Main은 미구현이다. Main fixture나 제안 인터페이스는 동작하는 Kotlin/MySQL
제품이 아니다. 현재 클라이언트 계약은
[`packages/ui-client`](../packages/ui-client/src/index.ts)이며, 아키텍처 그림에
맞추려고 가상의 그룹형 인터페이스로 교체하지 않는다.

Lite 수용과 모델 승인 이후에 시작한다. 이 로드맵은 병렬 구현이나 추가
에이전트 사용을 승인하지 않는다.

## 반드시 보존할 생명주기 결정

- 통합 요청서의 공통 승인자는 포함된 **모든** 작업과 Workspace의 승인 권한이
  있어야 한다. 없으면 생성을 차단한다. 해당 권한을 가진 한 사람이 전체를 한 번에
  승인한다. Workspace별 독립 승인을 모으는 방식이 아니다.
- 승인된 작업은 요청자, 승인자, 대상의 실행 권한 보유자가 철회할 수 있다.
  취소 권한의 상세 매핑은 #225/#227에서 설계하며 버튼 노출 여부로 추론하지 않는다.
- 전달 전 철회는 실행을 막는다. native 실행이 대기 중이면 명시적 취소를,
  실행 중이면 실제 중단 여부 확인을 제공한다. 배치 명령이 계속 수행되는데
  요청만 중단된 것처럼 표시하지 않는다.
- 취소는 실제 엔진 명령을 전송한다. 이미 끝났다면 플랫폼의 종결 증거를 우선한다.
  불확실한 상태를 완료로 만들지 않는다. 사유·행위자·대상과 요청/확정 결과를 보존한다.
- 실행 전달 실패가 확인되면 종결한다. 사용자는 현재 정책과 입력으로 새 요청을
  작성한다. 같은 요청의 재전달이나 자동 재전송은 승인된 목표에 없다.
  전달 결과를 모른다는 사실은 거절이 확인됐다는 뜻이 아니다.
- 결과 동기화는 플랫폼 증거로 저장된 관찰 상태를 보정하며 실행하거나 취소하지
  않는다. Main 첫 흐름의 필수 기능이다. 별도 Lite 결과 보정의 시점은 #225로
  앞당기지 않는다.
- 스케줄은 회차마다 가짜 승인을 만들지 않고 소유 배치의 승인된 형상을 사용한다.
  지연은 발생할 수 있으며 자동 몰아 실행이나 재시도는 승인하지 않았다.
  백필은 이후 별도 논의한다.
- Main 지연 모니터링은 #229의 필수 요구다. Lite는 worker 시작 시각으로 예정
  시각을 꾸며내 모니터링을 보장하는 것처럼 보이면 안 된다.

## 조회와 이력 수용 기준

페이지 크기는 검색 가능한 전체 이력의 크기가 아니다. 기간·배치 조회는 최초
페이지 밖의 기록도 찾을 수 있어야 한다. 미처리 소명과 관리자 검토는 오래됐어도
내처리함에 남는다. 부분 조회나 오류를 빈 결과 또는 전체 결과로 표시하지 않는다.

범위가 제한된 플랫폼 조회와 페이지 처리를 사용한다. 무제한 로딩, 별도 검색
서비스나 캐시를 도입하라는 요구가 아니다. 플랫폼 자체 삭제·보존 한계는 명시하며
제품의 조회 누락과 구분한다.

## QA와 전달 원칙

[요구사항 추적표](./requirements-traceability.ko.md),
[사용자 QA 시트](./user-qa.ko.md),
[QA 결과 양식](./qa-result-template.ko.md)은 동작 변경마다 함께 유지한다.
QA는 각 흐름에서 시작하며 5단계에 처음 하는 것이 아니다. 문서·코드·자동 검사·
사용자 QA·실제 플랫폼 증거·원격 CI·머지를 같은 완료로 취급하지 않는다.

- #119는 Lite/Main 전체 연결 UX 점검표로 열어 둔다.
- #65는 결정적인 브라우저 흐름 검증이며 #202의 실제 증거를 대체하지 못한다.
- BF-4/BF-5 다국어 표시와 UX-1 복귀 동선 잔여는 영향·후속 시점을 명시해
  수용받는다. 알려진 정확성 결함을 묵시적으로 면제하지 않는다.
- 공통 동작을 바꾸면 영향받는 Lite/Main 사용부를 재검증한다. #230은 누적된
  수용이며 영향 없는 모든 테스트 조합을 반복하라는 뜻이 아니다.
- 문서만 바꾸면 내용·포맷·링크·diff를 검사한다. 제품 테스트/빌드는 필요 없다.
- 원격 CI 확인과 머지는 사용자가 맡는다. 에이전트는 main에 머지하지 않는다.

## 릴리스 준비

#193(라이선스·보안 정책), #196(불변 Action 릴리스·업데이트/롤백·기본 브랜치 보호),
#68(정확한 사용·기여 안내)은 초기 Lite 릴리스를 포함한 첫 외부 사용자용 릴리스에
속한다. 모든 기능 변경의 선행 조건이 아니며 Main/Jenkins까지 미루지도 않는다.
외부 사용이나 기여를 초대한다면 라이선스를 더 먼저 결정한다.

문서에 불변 릴리스를 설명했다고 현재 개발용 Action 참조가 #196을 충족하는 것은
아니다. 릴리스 준비와 기능 준비를 구분한다.

## 승인이 더 필요한 아키텍처 상세

헥사고날 경계, Kotlin/Spring Boot, MySQL, 단일 소스 저장소, 공유 React UI는
수용된 방향이다. 정확한 Main ID·엔드포인트·스키마/테이블·주체 매핑·커넥터 인증·
job/plugin·배포 패키징은 #227/#228/#231의 설계 승인이 필요하다. 빈 모듈이나
범용 SDK를 미리 만들지 않는다.

기존 #192의 native 자원 발견·편입, 감사 내보내기, 외부 알림 채널, 실패 재발
분석 요구는 원래 ID와 우선순위를 유지한다. 상세 범위와 로드맵 배치는 사용자
확인이 필요하다. 확인 대기는 선택 기능으로의 하향이나 릴리스에서 누락할 권한을
뜻하지 않는다. 새 단계를 조용히 배정하거나 구현됐다고 주장하지 않는다.
