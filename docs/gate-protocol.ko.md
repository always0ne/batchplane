# BatchPlane Gate 계약

[English](./gate-protocol.md)

상태: 공통 의미와 현재 Lite 증적. 2026-10-05 정합화.
Main 전송 프로토콜·인증·사유 코드 매핑은 #227/#228이 필요하다.
현재 Lite Gate Action에는 `START | COMPLETE` 입력을 구현하지 않았다.

## 필수 통제 경계

통제 대상 업무는 실행 직전에 검증된 인가를 통과해야 한다. 필수 권한 근거가
없거나 유효하지 않거나 낡았거나 사용됐거나 검증 불가하면 Gate는 차단한다.
요청 ID, digest, label, 호출자가 보낸 행위자만으로는 권한 근거가 되지 않는다.

플랫폼 커넥터는 결정을 강제한다. 엔진마다 제품 정책을 따로 만들지 않는다.
직접 실행과 재실행도 지원 통제 범위 검토에 포함한다. 저장소·플랫폼 관리자는
인프라를 바꿀 수 있다. 특권 사용자의 모든 변조를 막는다고 약속하는 대신 그
신뢰 경계를 기록한다.

## 실제 Lite Action

실행 가능한 입출력 계약은 [actions/gate/action.yml](../actions/gate/action.yml)이다.
`result`, `reason_code`, `message`, `verified_sha`를 반환하며 범용 완료 작업을
구현하지 않는다. server mode 선언이 Main 서버 존재의 증거는 아니다.

수동 workflow: 검증된 요청·승인 -> dispatcher -> Gate -> 업무 job.
중복 승인이나 native 재실행으로 권한을 재사용하면 안 된다. 역할·화면 허용·조회
정합성은 #223, 실제 승인 입력 전달은 #212, 실패 요청 종결 목표는 #224다.

native 스케줄 workflow에서는 [schedule-request](../actions/schedule-request/action.yml)가
회차를 기록하고 Gate가 기록 성공을 확인한 허용 증적을 남긴다. 업무 진입 검증은
명령 전에 다시 검사하며 [schedule-result](../actions/schedule-result/action.yml)가
해당 attempt의 정확한 통제·업무 job 결과를 기록한다. 업무 job에는 이 기록을 위한
Issue 쓰기 권한을 주지 않는다.

NATIVE_SCHEDULE_V2의 기준은 [스케줄 실행 계약](./schedule-execution-contract.ko.md)이다.
이전 전결 승인 marker로 새 스케줄을 허용할 수 없으며 새 호환 기간도 필요 없다.

## 권한 근거

- 수동: 유효 Workspace 정책으로 승인된 정확한 실행 요청.
- 스케줄: 유효하게 승인된 소유 배치 형상과 일치하는 native 스케줄 맥락.
  수동 자가/자동 승인 모드와 독립적이다.

회차별 가짜 승인을 만들지 않는다. 스케줄 회차 Issue는 실행·증적 기록이지 새
사람 승인이 아니다. 긴급 우회는 승인된 범위가 아니다.

native 스케줄 권한 근거에는 이벤트 식별, 원본 workflow, 현재 활성 정의, 승인
형상, 스케줄, 원본 회차가 포함된다. worker가 늦게 시작했다는 이유만으로 정상
지연 이벤트를 거부하지 않는다. 생성·worker 시각으로 예정 시각을 추론하지 않는다.

## 식별·재사용·외부 효과

Lite 원본 회차 식별자는 `(repositoryId, batchId, scheduleId, sourceRunId)`의 정규
전체 SHA-256 표현이다. 실제 attempt 번호는 증적을 연결하며 새 권한을 만들지 않는다.
앞선 통제 job을 건너뛰려는 재사용을 포함해 같은 Run의 전체·부분 재실행을 거부한다.

서로 다른 native Run이 같은 예정 회차에서 중복 제거된다고 보장하지 않는다.
workflow concurrency는 영속 유일성 기록이 아니다. 필수 증적 쓰기 성공을 업무
시작 전에 확인해야 한다. 쓰기 결과 불명은 맹목적인 재시도나 허용 분기의 근거가 아니다.

Main에서는 연결·플랫폼 범위로 인증한 native 식별자, 제품 권한, 승인 형상·입력을
사용한다. 구체적인 permit 발급·멱등 키·재사용 응답은 #227/#228의 설계 작업이다.

## 결과와 운영 명령

완료와 Gate 허용은 다른 사실이다. 차단된 시도는 업무 실패가 아니다. 결과가
없다고 성공·실패로 판단하지 않는다. 결과 보정은 같은 attempt를 참조하고 증거를
보존해야 한다.

전달 실패가 확인되면 그 요청은 끝나며 사용자가 새 요청을 제출한다. native
수락 여부가 불명이면 관찰되기 전까지 불명으로 남긴다. 자동 재시도, 확인된 실패
이후 같은 요청 재전달, native 재실행에 대한 묵시적 인가는 승인된 목표가 아니다.

승인 후 철회는 명령·전달·Gate 경로에서 다시 검사해야 한다. 대기·실행 중 시도는
사유와 관찰 가능한 플랫폼 결과를 갖춘 명시적인 실제 취소/중단이 필요하다.
결과 동기화는 관찰 상태만 보정한다. #225와
[로드맵 생명주기 결정](./control-plane-migration-plan.ko.md)을 참조한다.

## Main 커넥터 설계 경계

이전 `batchplane.io/gate/v1` 시작/완료 메시지 형식은 공개된 프로토콜이 아니다.
#227/#228에서 버전·정확한 필드·신원 인증·권한 매핑·시간·사유 코드를 승인한 뒤
구현해야 한다.

GitHub OIDC와 Jenkins 설치 자격 증명/plugin은 연동 후보이지 현재 제품의 보장이
아니다. #231에서 실제 업무 전 Jenkins 연동을 선택하고 직접·재실행 통제 범위를
검증한다. 가상 커넥터 프레임워크나 대체 경로를 만들지 않는다.

Main과 Lite는 안정적인 제품 결정 의미로 수렴해야 한다. 이 문서로 기존 Lite
진단 코드명을 조용히 바꾸지 않는다. 새 매핑에는 정합성 fixture와 실제 계약·UI
변경이 필요하다.

## 증적과 수용

행위자·서비스 신원, native 실행/attempt, 요청·스케줄 권한 근거, 승인 형상/입력
digest, 결정·사유·확인 가능한 시각을 기록한다. 토큰·비밀값은 기록하지 않는다.
허용·차단 시도는 동일한 운영 이력 수준에서 보이며 저장 실패도 정확히 표시해야 한다.

#202는 실제 GitHub 스케줄/Gate/결과와 재실행 증거를 위해 계속 열어 둔다.
[QA 시트](./user-qa.ko.md)는 로컬 사례·실환경 증거·예정 명령을 구분한다.
문서의 설명이 이 증거를 대신하지 않는다.
