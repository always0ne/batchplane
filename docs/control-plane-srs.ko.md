# BatchPlane 통합 배치 통제 플랫폼 SRS

[English](./control-plane-srs.md)

상태: 2026-10-05 제품 요구사항 정합화.
작업 순서·구현 준비 상태는 이 규범적 목표와 별도다.
[로드맵](./control-plane-migration-plan.ko.md)과
[요구사항 추적표](./requirements-traceability.ko.md)를 참조한다.

원래 요구사항 ID와 우선순위를 유지한다. CP-BAT-004/005/006, CP-FAL-003/006,
CP-AUD-005, CP-NOT-002/003/004/005는 기존 P0 기준선에 포함됐지만 새 확정
로드맵에 명시적 배치가 없다. 기존 MUST/SHOULD 수준을 여기서 낮추지 않는다.
작업 배치와 상세 범위의 사용자 확인이 필요하다. 로드맵 누락이나 질문 대기가
요구 삭제·선택 기능화·구현 완료를 뜻하지 않는다. 보존 상세, Main API/DB 구조,
플랫폼 자격 증명은 배정된 단계에서 설계한다.

이 문서는 Main/Lite 공통 제품 수준 요구사항을 정의한다. 에디션별 명세는 저장·
전송·사용자 인계를 구체화할 수 있지만 여기서 정한 제품 의미를 바꿀 수 없다.

## 요구 수준

- `MUST`: P0 제품 계약의 필수 요구다.
- `SHOULD`: 에디션·플랫폼이 정당한 이탈 사유를 기록하지 않는 한 충족하는 것이 원칙이다.
- `MAY`: 선택 동작이다.

## 행위자

- `Requester`: 통제 변경·실행을 제안한다.
- `Approver`: 승인·반려를 결정한다.
- `Operator`: 배치 운영을 수행·모니터링한다.
- `Workspace Manager`: 연결·정책·후속 검토를 관리한다.
- `Auditor`: 운영 상태를 바꾸지 않고 증거를 조회한다.
- `Platform Service`: 인증된 플랫폼 측 Action·plugin·agent·webhook 발신자다.
- `BatchPlane Automation`: dispatcher·대조 보정기·알림기·outbox worker다.

## Workspace와 플랫폼 연결

- `CP-WSP-001` 사용자는 여러 Workspace에 소속될 수 있어야 한다(MUST).
- `CP-WSP-002` Main은 한 Workspace에 여러 플랫폼 연결을 지원해야 한다(MUST).
  Lite는 한 세션에서 여러 저장소 기반 Workspace의 동시 연결을 지원해야 한다(MUST).
  실제로 없는 저장소 간 공통 정책 권한 주체를 암시해서는 안 된다(MUST NOT).
- `CP-WSP-003` 플랫폼 연결은 플랫폼, 엔드포인트/설치, 자격 증명 참조, 지원 기능,
  연결 상태, 강제 통제 범위를 식별해야 한다(MUST).
- `CP-WSP-004` Main 플랫폼 자격 증명은 저장 후 UI로 반환하면 안 된다(MUST NOT).
  Lite 브라우저 토큰은 CP-WSP-006을 따른다.
- `CP-WSP-005` Main은 브라우저가 제공한 장기 토큰을 UI 상태에 저장하지 않고
  비밀정보 제공 경계를 통해 자격 증명 참조를 저장해야 한다(MUST).
- `CP-WSP-006` Lite의 GitHub 자격 증명은 휘발성 세션 저장소에만 둬야 하며(MUST),
  브라우저 신뢰 한계를 문서화해야 한다(MUST).
- `CP-WSP-007` 통합 조회를 포함한 목록·상세·명령·감사 조회는 인가된
  Workspace/연결 범위를 명시적으로 유지해야 한다(MUST). UI 선택 자체가 접근
  권한을 주면 안 된다(MUST NOT).
- `CP-WSP-008` 연결 상태는 인증 실패·플랫폼 불가·커넥터 비호환·Gate 미설치·
  관찰 저하를 구분해야 한다(MUST).
- `CP-WSP-009` 권한 기반 통합 조회·통합 요청은 단순 전환이 아니라 여러 Workspace에
  걸쳐야 한다(MUST). Lite가 우선이며 입증된 제약·사용자 승인 후에만 Main 첫 운영
  흐름 직후 첫 후속 과제로 미룰 수 있다.

## 플랫폼 지원 기능과 설치

- `CP-PRV-001` 모든 플랫폼은 안정적인 플랫폼 키·버전을 공개해야 한다(MUST).
- `CP-PRV-002` 모든 연결은 UI의 플랫폼명 조건 분기에 의존하지 않고 지원 기능을
  노출해야 한다(MUST).
- `CP-PRV-003` 지원 기능 선언은 목록·통제 변경·실행·취소·스케줄·실행 관찰·로그·
  Gate 강제·설치·연결 상태·대조 보정을 각각 다뤄야 한다(MUST).
- `CP-PRV-004` 미지원 동작은 플랫폼 사유와 함께 사용할 수 없음을 보여야 한다(MUST).
- `CP-PRV-005` 설치 상태는 커넥터 버전·호환성·강제 범위·필요 업그레이드를
  보고해야 한다(MUST).
- `CP-PRV-006` 플랫폼은 선언한 모든 기능의 Adapter TCK를 통과해야 한다(MUST).
- `CP-PRV-007` 플랫폼은 오류를 제품 오류 코드로 정규화하되 운영자를 위한 제한된
  native 진단을 보존해야 한다(MUST).
- `CP-PRV-008` 관리 커넥터·Action은 정확한 버전을 기록해야 한다(MUST). 운영
  템플릿은 승인된 불변 릴리스 ref·commit SHA를 사용해야 하며(MUST), 이동하는
  개발 브랜치를 운영 설치로 취급하면 안 된다(MUST NOT).

## 배치 목록과 편입

- `CP-BAT-001` Workspace의 플랫폼 연결을 아우르는 단일 배치 목록을 제공해야 한다(MUST).
- `CP-BAT-002` 배치는 전역 배치 ID와 별도 native 외부 자원 참조를 가져야 한다(MUST).
- `CP-BAT-003` 핵심 배치 모델은 GitHub workflow 경로·Jenkins Job 이름·runner
  label 등 플랫폼 전용 식별자를 필수로 요구하면 안 된다(MUST NOT).
- `CP-BAT-004` 플랫폼은 기존 native 배치 발견을 지원하는 것이 원칙이다(SHOULD).
- `CP-BAT-005` 발견한 배치는 통제·미통제·부분 통제·누락·형상 불일치로 분류해야 한다(MUST).
- `CP-BAT-006` 편입을 지원하는 플랫폼은 native 자원을 다시 만들지 않고 기존
  배치를 BatchPlane 배치에 연결할 수 있어야 한다(MUST).
- `CP-BAT-007` 활성 통제 배치는 유효 형상·플랫폼 연결·플랫폼·정책·스케줄 요약·
  강제 상태·최근 실행 상태를 식별해야 한다(MUST).
- `CP-BAT-008` 삭제된 배치·과거 형상·요청·실행·실패·감사도 직접 조회할 수 있어야 한다(MUST).

## 통제된 등록·변경·삭제

- `CP-CHG-001` 등록·수정·삭제는 변경 요청으로 시작해야 하며(MUST) 인가 전에 native
  플랫폼을 바꾸면 안 된다(MUST NOT). 지원하는 정지·복구도 통제 변경이다. 이것이
  별도 신규 정지 기능의 승인은 아니다.
- `CP-CHG-002` 변경 요청에는 요청자·사유·대상·작업 유형·기준 형상·제안 형상·
  정규 diff·가능한 native diff·요청 digest가 있어야 한다(MUST).
- `CP-CHG-003` 승인자는 원시 YAML·native 설정부터 해석하지 않아도 중요한 변경
  맥락을 화면에서 볼 수 있어야 한다(MUST).
- `CP-CHG-004` 승인 요청 반영 시 승인 이후 대상 기준 형상이 바뀌지 않았는지
  검증해야 한다(MUST).
- `CP-CHG-005` 기준 형상이 낡았으면 충돌 처리해야 하며(MUST) 조용히 반영하면 안 된다(MUST NOT).
- `CP-CHG-006` 플랫폼 변경은 멱등적이어야 하며(MUST) native 작업 ID·결과를
  기록해야 한다(MUST).
- `CP-CHG-007` 플랫폼 생성 PR·native review는 구현 증거로 유지할 수 있다(MAY).
  다만 Workspace 정책이 명시적으로 요구하지 않으면 Main은 두 번째 독립 제품
  승인을 요구하면 안 된다(MUST NOT).
- `CP-CHG-008` Lite는 PR을 변경 요청과 승인 화면으로 함께 사용할 수 있다(MAY).
- `CP-CHG-009` 직접 외부 변경은 대조 보정으로 탐지하고 형상 불일치·미통제 변경
  증적으로 보고해야 한다(MUST).

## 승인과 직무 분리

- `CP-APR-001` 승인 정책은 플랫폼 역할이 아닌 BatchPlane 내부 역할로 표현해야 한다(MUST).
- `CP-APR-002` 외부 사용자·그룹·팀·저장소 역할은 신원 어댑터로 내부 역할에
  매핑할 수 있다(MAY).
- `CP-APR-003` 모든 결정은 결정 시 평가한 정책 형상·대상 digest를 식별해야 한다(MUST).
- `CP-APR-004` 반려에는 사유가 필수다(MUST).
- `CP-APR-005` 기본값은 자가승인 금지여야 한다(MUST).
- `CP-APR-006` 명시적 Workspace 정책으로 자가승인·자동 인가를 허용할 수 있으나(MAY),
  그 증적은 완화 모드를 식별해야 한다(MUST).
- `CP-APR-007` 이후 정책 변경이 기록된 결정의 과거 의미를 바꾸면 안 된다(MUST NOT).
- `CP-APR-008` 승인과 실행 인가는 별도로 모델링해야 한다(MUST).
- `CP-APR-009` 낡음·만료·취소·사용 완료·현재 대상 불일치 상태의 승인 작업으로
  새 인가를 만들면 안 된다(MUST NOT).
- `CP-APR-010` 정책·역할 바인딩·자격 증명·설치 제안은 제안 전 유효 정책으로
  인가해야 하며(MUST), 제안 값으로 자신을 인가하면 안 된다(MUST NOT).

## 실행 의도와 인가

- `CP-EXE-001` 수동·API·상위 요청·스케줄·native 트리거는 정규 실행 의도 또는
  스케줄 회차 맥락에 매핑해야 한다(MUST).
- `CP-EXE-002` 수동 실행은 요청자·사유·파라미터·대상 형상·workflow/Job 대상·
  만료·요청 digest를 기록해야 한다(MUST).
- `CP-EXE-003` 민감 파라미터 값은 감사 텍스트·요청 body·브라우저 저장소·로그에
  기록하면 안 된다(MUST NOT). digest·비밀 참조는 기록할 수 있다(MAY).
- `CP-EXE-004` 승인은 정규화된 실행 의도 전체에 결합해야 한다(MUST).
- `CP-EXE-005` Main 실행 허용은 실제 attempt에 대한 검증되고 범위가 제한된
  인가에 결합해야 한다(MUST). Execution Permit은 표현 후보이며 발급 시점·전송은
  Main 계약 승인이 필요하다.
- `CP-EXE-006` permit은 Workspace·플랫폼 연결·배치·형상·트리거·요청/스케줄
  권한 근거·파라미터 digest·만료·알 수 있는 의도된 native 실행에 결합해야 한다(MUST).
- `CP-EXE-007` 사용자가 새 실행을 요청하면 새 인가가 필요하다(MUST). native
  재실행은 소비한 권한을 재사용하면 안 된다(MUST NOT). 자동 실행 재시도나 확인된
  전달 실패 후 같은 요청 재전달은 승인하지 않았다.
- `CP-EXE-008` 확인된 전달 실패는 요청을 종결하고 현재 정책·입력의 새 요청을
  요구해야 한다(MUST). 전달 불명·Gate 차단·업무 실패와 구분해야 한다(MUST).
- `CP-EXE-009` 승인 파라미터는 미승인 값으로 대체되지 않고 실제 업무 런타임에
  도달해야 한다(MUST). 저장된 요청만 정확해서는 부족하다.
- `CP-EXE-010` 만료·종결 실패 요청이 유효 후속 요청·변경을 영구 차단하면 안 된다(MUST NOT).
- `CP-EXE-011` 요청자·실제 승인자·대상 실행 권한자는 전달 전 승인 작업을 철회할
  수 있어야 한다(MUST). 명령·Gate에서 철회를 강제해야 하며(MUST) UI 상태만으로는 부족하다.
- `CP-EXE-012` 플랫폼 수락 후 철회는 실제 상태에 따라 분기해야 한다(MUST).
  명시적 대기 취소·실행 중단 확인, 실제 엔진 명령, 사유·행위자·대상 증거가 필요하다.
  이미 종결된 결과는 보존해야 하며(MUST) 불확실한 결과를 종료됐다고 선언하면
  안 된다(MUST NOT). 상세 취소 권한 매핑은 설계가 필요하다.
- `CP-EXE-013` Main 첫 실행 흐름은 취소와 별도로 결과 동기화를 제공해야 한다(MUST).
  실제 플랫폼 증거로 기록된 관찰을 보정하며 업무 명령을 재실행·중단하면 안 된다(MUST NOT).

## 스케줄 통제

- `CP-SCH-001` 별도 조회 모델에 저장하더라도 스케줄은 논리적으로 배치 형상에
  속해야 한다(MUST).
- `CP-SCH-002` 스케줄 등록·수정·활성·비활성·삭제는 통제된 변경이어야 한다(MUST).
- `CP-SCH-003` UI는 요청 생성 전에 cron·시간대·플랫폼 한계를 검증하고 향후 예정
  수행 시각을 보여야 한다(MUST).
- `CP-SCH-004` 스케줄 트리거는 native 배치 플랫폼이 맡는 것이 원칙이다(SHOULD).
- `CP-SCH-005` 현재 유효한 승인 스케줄 형상이 일치하는 각 회차의 인가 근거다.
- `CP-SCH-006` 회차는 사람 승인을 꾸며내거나 Workspace 자동승인 모드에 의존하면 안 된다(MUST NOT).
- `CP-SCH-007` 모든 회차는 승인 스케줄 형상에 연결된 별도 실행 시도·Gate 결정을
  만들어야 한다(MUST).
- `CP-SCH-008` 같은 native 회차의 중복 처리를 막으면서 중복 전달 증거는 보존해야 한다(MUST).
- `CP-SCH-009` native 플랫폼이 계속 트리거해도 비활성·삭제·불일치·대체된 스케줄은
  Gate에서 거부해야 한다(MUST).
- `CP-SCH-010` 플랫폼 지연·동시성·중복 한계를 명시해야 한다(MUST). 자동 몰아 실행·
  백필·실행 재시도는 승인하지 않았다. native 회차 ID가 추론한 예정 시각을 붙인
  별도 native 실행의 중복 제거까지 의미해서는 안 된다(MUST NOT).
- `CP-SCH-011` 배치 간 스케줄 조회에서 소유 배치·승인 근거·실행 이력으로 이동할
  수 있어야 한다(MUST). 편집은 배치 등록·변경 요청에서 한다.
- `CP-SCH-012` cron 검증·다음 회차 미리보기·생성 native 스케줄은 지원 표현식·
  시간대 의미가 일치해야 한다(MUST).
- `CP-SCH-013` Main은 지연 모니터링을 제공해야 한다(MUST). 모르는 예정 시각은
  불명으로 유지해야 하며(MUST), worker 시작 시각으로 예정 시각을 꾸며내면 안 된다(MUST NOT).

## Gate 강제

- `CP-GAT-001` 통제 업무는 첫 배치 명령·Job 본문 전에 Gate를 거쳐야 한다(MUST).
- `CP-GAT-002` Gate 정책은 BatchPlane Core가 소유해야 하며 플랫폼 커넥터가
  독립적으로 재구현하면 안 된다(MUST).
- `CP-GAT-003` 플랫폼 측 Gate 커넥터는 자신을 인증하고 요청을 native 실행
  식별자에 결합해야 한다(MUST).
- `CP-GAT-004` 인가 증거가 없거나 무효·만료·사용 완료·낡음·검증 불가하면
  Gate는 차단해야 한다(MUST).
- `CP-GAT-005` 허용·차단 시작 시도를 모두 기록해야 한다(MUST).
- `CP-GAT-006` 직접 native 실행·재실행·스케줄·API 트리거는 Gate를 우회해서는 안 된다(MUST).
- `CP-GAT-007` 완료는 시작 시 생성·인식한 같은 attempt를 갱신해야 하며(MUST)
  멱등적이어야 한다(MUST).
- `CP-GAT-008` 사유 코드는 안정적인 제품 계약이어야 하고(MUST) UI 경계에서만
  번역해야 한다(MUST).
- `CP-GAT-009` 시작 전 통제를 검증하지 못한 연결은 `UNPROTECTED` 또는
  `PARTIALLY_PROTECTED`로 표시해야 하며(MUST), 완전 통제로 보이면 안 된다(MUST NOT).
- `CP-GAT-010` 묵시적 허용 전환은 없다. 긴급 우회는 승인 범위가 아니며 향후
  제안에도 별도 설계·승인이 필요하다.
- `CP-GAT-011` 플랫폼 연동은 Gate가 허용한 모든 attempt의 종결 결과를 보고하거나
  명시적 `UNKNOWN`으로 대조 보정해야 한다(MUST). 시작 Gate 증거만으로는 완전한
  실행 기록이 아니다.

## 실행 관찰과 로그

- `CP-RUN-001` 실행 목록은 대기·실행 중·성공·업무 실패·Gate 차단·취소·시간 초과·
  불명 상태를 정규화해야 한다(MUST).
- `CP-RUN-002` 상세에는 플랫폼·native 실행 ID·배치·형상·트리거·행위자·요청/
  스케줄 권한 근거·Gate 결정·시작/종료 시각·native 원본 링크가 있어야 한다(MUST).
- `CP-RUN-003` Gate 차단과 업무 실패는 시각·의미상 구분해야 한다(MUST).
- `CP-RUN-004` native 로그는 필요 시 조회해야 하며(MUST) 기본값으로 감사 증거에
  영속 저장해서는 안 된다(MUST).
- `CP-RUN-005` 로그 접근은 Workspace·플랫폼 인가를 따라야 하고(MUST) 애플리케이션
  telemetry에 비밀정보를 노출하지 않아야 한다(MUST).
- `CP-RUN-006` 누락·지연 관찰은 실제 업무 결과와 구분해야 한다(MUST). 대조
  보정으로 새 실행을 만들면 안 된다(MUST NOT).
- `CP-RUN-007` 실행·감사 조회는 최초 페이지 밖의 기간·배치 일치 기록도 찾아야
  한다(MUST). 부분 범위·오류를 완전·빈 결과로 표현하면 안 된다(MUST NOT).
- `CP-RUN-008` 실행 상세는 정확한 요청/권한 근거·보존 배치 형상에 연결해야 한다(MUST).
  업무 로그는 실제 배치 명령 구간이 기본이며 전체보기도 제공해야 한다(MUST).

## 실패 후속처리

- `CP-FAL-001` 업무 실패는 후속처리 건을 생성·노출해야 한다(MUST). Gate 차단은
  업무 실패가 아닌 통제 예외로 유지해야 한다(MUST).
- `CP-FAL-002` 후속처리에는 원인 분류·소명·조치·담당자·기한 상태·작성자·관련
  attempt가 있어야 한다(MUST).
- `CP-FAL-003` 원인 분류는 Workspace에서 설정 가능하고 재발 분석에 충분히 안정적이어야 한다(MUST).
- `CP-FAL-004` 제출한 후속처리는 종결 전 Workspace 관리자 검토를 받아야 한다(MUST).
- `CP-FAL-005` 검토 승인·반려·보완 요청은 별도의 불변 결정이어야 한다(MUST).
- `CP-FAL-006` 배치·원인·플랫폼·담당자별 반복 실패는 개별 증거를 잃지 않는 보고서로
  제공하는 것이 원칙이다(SHOULD).

## 감사와 증적

- `CP-AUD-001` 사용자·자동화·정책·Gate·플랫폼 변경·대조 보정·실패 검토 동작은
  감사 이벤트를 생성해야 한다(MUST).
- `CP-AUD-002` 지원 제품 API에서 감사 기록은 추가 기록 전용이어야 한다(MUST).
- `CP-AUD-003` 이벤트에는 행위자 유형·신원·Workspace·대상·동작·결과·사유·발생
  시각·연결 ID·증거 출처가 있어야 한다(MUST).
- `CP-AUD-004` 중요 변경은 전후 형상 참조 또는 정규 digest를 포함해야 한다(MUST).
- `CP-AUD-005` Main은 시각·Workspace·배치·요청·실행 시도·행위자·플랫폼·결과로
  내보내기를 지원해야 한다(MUST).
- `CP-AUD-006` 보존은 배포 정책으로 설정할 수 있어야 한다(MUST). 기본 보존 설명이
  특정 관할 규제 준수를 뜻하지 않는다.
- `CP-AUD-007` Lite는 저장소 증거를 같은 감사 의미로 변환해야 하며(MUST) native
  원본 링크를 보존해야 한다(MUST).

## 알림과 작업함

- `CP-NOT-001` 내처리함은 요청·승인·실패 실행·후속처리·관리자 검토에서 처리할
  항목을 도출해야 한다(MUST). 미처리는 오래됐거나 첫 페이지 밖이어도 찾고 처리할
  수 있어야 한다(MUST).
- `CP-NOT-002` Main 알림은 커밋된 상태에서 outbox를 통해 생성해야 한다(MUST).
- `CP-NOT-003` 알림 전달 실패로 통제 업무 트랜잭션을 롤백하면 안 된다(MUST NOT).
- `CP-NOT-004` 알림 어댑터는 도메인 상태 전이를 바꾸지 않고 이메일·채팅·webhook
  등의 채널을 지원할 수 있다(MAY).
- `CP-NOT-005` 알림의 상세 링크는 native 플랫폼 링크보다 먼저 해당 BatchPlane
  상세 화면을 여는 것이 원칙이다(SHOULD).

## 공유 UI

- `CP-UI-001` Main/Lite는 같은 React/Vite 소스 트리를 사용해야 한다(MUST).
- `CP-UI-002` 서로 다른 runtime bootstrap으로 별도 빌드를 만들 수 있다(MAY).
- `CP-UI-003` Page는 애플리케이션 수준 의존 주입으로 제품 클라이언트/runtime을
  받아야 하며(MUST) GitHub 클라이언트를 직접 생성하면 안 된다(MUST NOT).
- `CP-UI-004` 제품 경로·주요 표시명은 플랫폼 중립적이어야 한다(MUST).
- `CP-UI-005` 플랫폼 경로·Job 이름·로그·원본 링크는 native 증거로 표시할 수 있다(MAY).
- `CP-UI-006` 배치·실행·실패·요청·감사 목록은 해당하는 Workspace·플랫폼·연결
  맥락을 지원해야 한다(MUST).
- `CP-UI-007` UI 지원 기능 검사는 플랫폼명 문자열 비교가 아니라 runtime/플랫폼
  descriptor를 사용해야 한다(MUST).
- `CP-UI-008` 기본 locale은 영어이며 한국어를 포함한다. 기여자는 기능 로직 변경
  없이 locale 리소스를 추가할 수 있어야 한다(MUST).

## Main 런타임과 저장

- `CP-MAIN-001` 서비스 분해를 고려하기 전에 Kotlin/Spring Boot 모듈형 모놀리스로
  구현해야 한다(MUST).
- `CP-MAIN-002` Main은 트랜잭션 상태 변경과 MySQL을 사용해야 한다(MUST).
- `CP-MAIN-003` 현재 상태·추가 기록 감사·outbox는 같은 MySQL 배포를 공유할 수
  있으나(MAY) 테이블 책임을 분리해야 한다(MUST).
- `CP-MAIN-004` 외부 효과는 상태 커밋 후 멱등 worker나 명시적으로 복구 가능한
  오케스트레이션으로 수행해야 한다(MUST).
- `CP-MAIN-005` 플랫폼 자격 증명은 암호화하거나 외부 비밀 관리 어댑터 뒤에 저장해야 한다(MUST).
- `CP-MAIN-006` 스키마 변경은 버전이 있는 migration을 사용해야 한다(MUST).

## 신뢰성과 보안

- `CP-NFR-001` 모든 명령 엔드포인트는 멱등 키를 요구하거나 안정적인 작업 키를
  도출해야 한다(MUST).
- `CP-NFR-002` webhook·플랫폼 이벤트는 최소 한 번 전달로 취급해야 한다(MUST).
- `CP-NFR-003` 제품 전이의 멱등성을 외부 업무 효과의 exactly-once 보장으로 표현하면
  안 된다(MUST NOT). native 수락 불명으로 맹목적 재전송을 하면 안 된다(MUST NOT).
- `CP-NFR-004` 절대 시각은 명확한 UTC 의미를 가져야 한다(MUST). 스케줄 시간대는
  단순 표시 선호가 아니라 실행 입력이므로 보존해야 한다(MUST). 실제 플랫폼 정밀도를 보존한다.
- `CP-NFR-005` 제품 로그에서 로그·토큰·자격 증명·민감 파라미터·신원 assertion을
  마스킹해야 한다(MUST).
- `CP-NFR-006` Workspace 접근은 UI 필터뿐 아니라 애플리케이션·조회 경계에서
  강제해야 한다(MUST).
- `CP-NFR-007` rate limit·플랫폼 장애·webhook 지연·대조 보정 지연은 관찰 가능해야 한다(MUST).
- `CP-NFR-008` 가용성·처리량·RPO·RTO·감사 보존·최대 내보내기 크기는 운영 릴리스
  전에 배포 조건별 결정으로 기록해야 한다(MUST).

## 통합 요청서

- `CP-REQ-001` 한 요청서가 여러 배치·작업 유형·인가된 Workspace를 포함하고
  전체 한 번의 승인을 지원해야 한다(MUST).
- `CP-REQ-002` 모든 대상 작업의 승인 권한을 가진 사람이 없으면 생성을 차단해야
  한다(MUST). 공통 승인자가 전체를 한 번 결정하며 Workspace별 독립 승인은 대안이 아니다.
- `CP-REQ-003` 전체 요청 승인은 항목 실행 결과와 분리해야 한다(MUST). 대기·실행 중·
  종결이 섞인 대상을 일부 수행 중인데 전체 철회로 표시하면 안 된다(MUST NOT).
- `CP-REQ-004` 통합 요청 제공 전까지 기존 요청 경로를 유지해야 한다(MUST).
  향후 경로는 `/requests/new`, `/requests/:requestId`다.

## 추적

[요구사항 추적표](./requirements-traceability.ko.md)는 모든 CP 묶음과 통합 요청
명세를 담당 이슈·QA에 연결한다. 제안 범위·Main 상세를 구현됐다고 주장하지 않는다.
이탈 기록에는 요구·사유·사용자 영향·대응·수용한 후속 작업을 적는다.

[QA 시트](./user-qa.ko.md)는 요구당 테스트 하나를 요구하지 않고 관찰 가능한
사용자 흐름으로 묶는다. 구현·로컬 자동 검사·사용자 QA·실제 플랫폼 수용은 별도 상태다.
