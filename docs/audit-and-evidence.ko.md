# BatchPlane 감사와 증적

[English](./audit-and-evidence.md)

상태: 제품 증적의 의미와 Main 설계 후보. 2026-10-05.
정확한 메시지 형식·스키마·보존 설계는 미구현이다. 기존 내보내기·재발 보고 요구는
우선순위를 유지하며 상세 범위와 로드맵 배치는 사용자 확인을 기다린다.
[로드맵](./control-plane-migration-plan.ko.md)을 참조한다.

## 목적

BatchPlane 감사는 각 통제 작업에서 누가 요청·승인·반영·시도·허용·거부·실행·실패·
소명·검토했는지 답해야 한다. 제품 상태를 native 플랫폼 증거에 연결하되 원시
플랫폼 로그를 불변 제품 원장이라고 주장해서는 안 된다.

## 증적 계층

| 계층        | 목적                   | Main                         | Lite                                                |
| ----------- | ---------------------- | ---------------------------- | --------------------------------------------------- |
| 제품 상태   | 현재 처리 가능한 상태  | MySQL 상태 테이블            | 저장소 증적에서 도출                                |
| 결정 증적   | 승인·Gate·검토         | 추가 기록 전용 MySQL 행 예정 | 원본 권한의 영향을 받는 GitHub PR/Issue 댓글·review |
| 감사 이벤트 | 검색·내보내기 타임라인 | `audit_event`                | 정규화된 조회 모델                                  |
| Native 증거 | 플랫폼 작업·실행 출처  | 증거 참조                    | GitHub 원본 URL/ID                                  |
| 원시 로그   | 문제 조사              | 필요 시 조회                 | 필요 시 조회                                        |

원시 로그는 기본적으로 사라질 수 있는 운영 증거다. 비밀정보를 포함하거나 크기가
클 수 있으며 BatchPlane 감사 보존보다 플랫폼 보존 정책을 따를 수 있다.

## 필수 이벤트 유형

### 신원과 접근

- 정책상 기록 가능한 인증 성공·실패
- Workspace 소속·역할 바인딩 변경
- 정책 형상 생성·활성화
- 비밀값을 제외한 플랫폼 자격 증명 생성·교체·폐기
- 민감 명령의 인가 거부

### 플랫폼 연결

- 연결 생성·변경·비활성화·삭제
- 지원 기능·호환성 변경
- 설치·업그레이드 계획과 반영
- 상태 또는 강제 통제 범위 변경

### 배치와 스케줄

- 발견·편입(상세 범위·배치 대기)
- 등록·변경·삭제 요청 제출
- 승인·반려·취소
- 플랫폼 반영 시작·완료·실패
- 형상 활성화
- 스케줄 형상 활성화·비활성화·삭제
- 형상 불일치·통제 밖 변경·native 자원 누락 탐지

### 실행과 Gate

- 실행 의도 요청·승인·반려·취소·만료
- 전달 시작·수락·확인된 실패·여전히 결과 불명
- 행위자·사유를 포함한 철회/취소 요청·확정·미확정
- native 시작 관찰
- Gate 허용·차단
- native 실행 시작·완료·취소·시간 초과
- 이벤트 상충·대조 후 보정
- 직접 또는 미인가 native 시도 탐지

### 실패 후속처리

- 실패 건 생성
- 소명·조치 제출
- 관리자 승인·반려·보완 요청
- 건 종결. 재발 보고는 요구를 유지하며 상세·배치 대기

## 추가 기록 전용 규칙

- 지원하는 애플리케이션 API는 기존 감사 이벤트를 수정·삭제하지 않는다.
- 보정은 대체·수정 대상 이벤트를 참조하는 새 이벤트를 만든다.
- 제품 명령은 결정·Gate 증적·과거 배치 형상·실패 제출·관리자 검토를 덮어쓰지
  않고 추가한다. Lite는 GitHub 원본 저장소의 불변성을 보장할 수 없다.
- 현재 상태 조회 모델은 바뀔 수 있지만 전이 시 이벤트를 생성한다.
- DB 관리는 특권 인프라 위험으로 남으며 배포 통제·백업·접근 로그·내보내기
  정책으로 다뤄야 한다.

애플리케이션의 추가 기록 방식만으로 규제 준수를 증명하지 못한다. 배포·조직
통제가 여전히 필요하다.

## 정규 Digest

중요한 통제 객체는 정규 직렬화와 SHA-256 digest를 사용한다.

- 변경 요청의 제안 형상·변경 계획
- 실행 의도와 비밀이 아닌 파라미터 바인딩
- 승인 대상
- 배치·스케줄 형상
- Gate 요청 식별
- 감사 전후 참조

정규화 규칙과 테스트 벡터는 언어 중립적이다. 같은 fixture에서 Kotlin·TypeScript·
플랫폼 커넥터가 동일 digest를 생성해야 한다.

digest는 불일치를 탐지할 뿐 인가 자격 증명이 아니다.

## 기록 연결

감사 조회는 다음 기준을 지원한다.

- Workspace와 플랫폼 연결
- 플랫폼과 외부 자원
- 배치와 배치 형상
- 변경 요청과 승인 건
- 실행 의도·스케줄 형상·실행 시도
- Gate 결정과 native 실행
- 실패 건과 검토
- 주체·작업·결과·사유 코드
- 기간과 연결/trace ID

하나의 사용자 타임라인이 여러 생명주기의 이벤트를 합칠 수 있지만 각 대상·출처는
보존해야 한다.

## Main 트랜잭션 경계

상태 변경 Main 명령은 MySQL 트랜잭션 하나에 다음을 쓴다.

1. aggregate·현재 상태 변경
2. 해당하는 불변 결정·형상 기록
3. 추가 기록 전용 감사 이벤트
4. 승인된 복구 가능 오케스트레이션의 외부 효과 의도. outbox는 후보이지 미리 선택한
   범용 알림 프레임워크가 아니다.

외부 플랫폼 호출은 커밋 후 수행한다. 그 결과로 별도의 멱등 상태 전이·감사 이벤트를
만든다.

## Lite 조회 모델

Lite는 GitHub 증적을 공통 이벤트 의미로 매핑한다.

- 머지된 통제 PR -> 변경 승인·반영 이벤트
- Issue body -> 실행 의도 증적
- 승인·반려 댓글 -> 결정 이벤트
- dispatcher marker·댓글 -> 전달 이벤트
- Gate Action 결과 -> Gate 결정 이벤트
- workflow run -> 실행 시도 이벤트
- 실패·검토 댓글 -> 후속처리 이벤트

파서는 원본 URL·저장소·번호/ID·행위자·native 시각을 보존한다. 기존 과거 namespace
조회기는 현재 코드에 남아 있지만 이 문서가 새 호환 계층을 요구하지는 않는다.
과거 전결 스케줄 승인은 유효 실행 권한이 아니다. NATIVE_SCHEDULE_V2는 소유
승인 형상, 원본 회차, 정확한 job/attempt 결과를 사용한다.

## 내보내기 요구와 미확정 제공 설계

원래 요구와 우선순위를 유지한다. 상세 형식·배치는 사용자 확인이 필요하며 이
문서가 내보내기를 제거하거나 구현하지 않는다. 이전 Main 내보내기 기준은 기계가
읽을 JSON/NDJSON과 사람이 읽을 보고서 형식을 요구한다. 내보내기에는 다음을 포함한다.

- 명시적인 조회 범위·생성 시각
- 제품·스키마 버전
- 순서가 있는 이벤트
- 증거 참조
- 내보내기 manifest·내용 digest
- 플랫폼 증거를 얻지 못했을 때의 원본 불완전 경고

전달 방식과 정확한 내보내기 형식은 별도 설계가 필요하며 접근 인가가 필수다.
감사 데이터 내보내기 자체도 감사한다.

## 보존과 개인정보

- 배포 정책·증거 유형에 따라 보존을 설정할 수 있다.
- 과거 배치·실행 증거는 배치 삭제 이후에도 남아야 한다.
- 만료·삭제는 임의 UI 삭제가 아니라 감사 가능한 보존 job을 따라야 한다.
- 감사의 개인정보는 안정적인 식별과 필요한 표시 맥락으로 최소화한다.
- 비밀값·접근 토큰·원시 신원 assertion·민감 파라미터는 금지한다.
- 별도 설계한 안전한 로그 보존 기능으로 명시적으로 보관하지 않는 한 플랫폼 원시
  로그는 플랫폼 보존 정책을 따른다.

배포 환경의 법무·보안·운영 요구가 확인되기 전에는 제품 아키텍처에서 보존 기간을
고정하지 않는다.

## 조회 완전성과 운영 증거

기간·배치 조회는 첫 페이지 밖의 기록에 닿아야 한다(#226). 오래된 미처리 소명·
검토도 내처리함에서 처리할 수 있어야 한다. 권한 부족·부분 조회·플랫폼 보존 한계를
빈 타임라인이나 완전한 타임라인으로 표현하지 않는다.

취소는 요청과 실제 엔진 확인을 따로 기록한다. 결과 동기화는 플랫폼 증거로 보정하며
실행·취소하지 않는다. 확인된 전달 실패는 종결이고 새 요청은 새 인가 이력을 가진다.
수락 여부 불명을 실패로 만들지 않는다. [사용자 QA](./user-qa.ko.md)를 참조한다.

## 무결성과 운영

Main 운영 배포는 다음을 지원하는 것이 바람직하다.

- 감사 테이블 쓰기 접근 제한
- 전송·저장 암호화
- DB 백업·복구 테스트
- 순서 누락, outbox 지연, 대조 보정 지연, 내보내기 실패 모니터링
- 시각 동기화와 UTC timestamp 검증

이 기준선은 hash-chain 서비스나 새 증적 저장소를 승인하지 않는다. 배포 보강은
입증된 요구를 다뤄야 하며 기존 접근 통제·증적 책임을 대체해서는 안 된다.
