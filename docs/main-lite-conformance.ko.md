# Main과 Lite 정합성

[English](./main-lite-conformance.md)

상태: 2026-10-05 정합화한 수용 계획. Main은 미구현이다.

## 같은 의미, 다른 구현

하나의 React 제품 UI가 [현재 제품 클라이언트](../packages/ui-client/src/index.ts)를
호출한다. Lite는 GitHub 증적을, Main은 Kotlin API와 MySQL을 사용한다.
동등한 제품 동작은 권한·상태·증적에서도 동등한 의미를 가져야 한다.

가상의 병렬 클라이언트나 영구 호환 기간을 요구하지 않는다. 기존 과거 기록
조회기가 오래된 전결 스케줄 증적으로 새 실행을 허용하는 것은 아니다.
새 스케줄 기록은 [NATIVE_SCHEDULE_V2](./schedule-execution-contract.ko.md)를 따른다.

## 필수 흐름 비교

| 흐름           | 공통 수용 기준                                                                               | 에디션별 사실                                  |
| -------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 등록·변경·삭제 | 정확한 형상/diff 승인, 낡은 내용 거부, 삭제 후 이력 보존                                     | Lite는 PR 증적, Main은 제품 기록과 플랫폼 반영 |
| 승인           | 유효 정책, 실제 결정 행위자, 자가/자동 모드, 모든 대상의 공통 권한                           | 신원 어댑터는 달라도 권한 의미는 같음          |
| 수동 실행      | 승인 입력을 업무에 전달. 전달·Gate·결과를 구분                                               | GitHub dispatcher와 Main 오케스트레이션        |
| 스케줄 실행    | 승인된 소유 형상, 회차별 승인 없음, Gate와 실제 결과 연결                                    | 플랫폼 native 스케줄 식별자와 시간 한계        |
| 철회·취소      | 상태별 확인, 실제 취소, 요청/확정 결과 구분                                                  | 실제 플랫폼 명령과 인증                        |
| 결과 동기화    | 관찰 상태만 보정. 실행·취소하지 않음                                                         | Main 첫 흐름 필수. Lite 추가 제공 시점은 별도  |
| 로그·실패      | 업무/Gate 구분, 정확한 실행, 업무/전체 로그, 명시적 관리자 검토                              | native 로그 보존과 접근 권한                   |
| 조회           | 범위에 맞는 완전한 기간·배치 검색, 내처리함 미처리 보존, 부분 조회를 빈 결과로 표시하지 않음 | GitHub 페이지 처리와 Main 조회 모델            |
| 통합 요청      | 복수 배치·유형·Workspace. 전체 작업의 공통 승인자 한 명                                      | #142 Lite 실현 가능성 기준과 Main 기본 모델    |
| 감사           | 행위자·권한·형상·결과·출처 추적                                                              | Lite 증적은 GitHub 권한으로 편집·삭제 가능     |

승인 모드가 자격 있는 관리자의 자가 검토를 허용할 수는 있지만 실패 소명을
조용히 자동 종결하지 않는다. Gate 차단이 새 업무 실패 소명 의무를 만드는 것은 아니다.

## 플랫폼 제약과 정확한 설명

native 식별자, 시간대 지원, 파라미터 타입, 로그 보존, 실제 취소 의미를 플랫폼마다
기록한다. 지원하지 않는 의미를 조용히 흉내 내지 않는다. native 회차 키는 독립적으로
만들어진 Run 사이의 exactly-once 업무 수행을 증명하지 않는다.

capability는 실제 지원 여부를 나타내며 필수 작업을 영구히 감추는 이유가 아니다.
Lite #225는 Lite 수용 전에 마쳐야 한다. Main GitHub와 초기 Jenkins에서 취소와
결과 동기화를 실제로 검증해야 한다.

저장소 기반 Lite Workspace는 개별 신뢰 경계를 유지한다. 선택 저장소를 전환하는
기능만으로 #142를 충족하지 못한다. Main은 한 Workspace의 여러 플랫폼 연결을 지원한다.

## 증거 전략

[요구사항 추적표](./requirements-traceability.ko.md)와 [QA 사례](./user-qa.ko.md)를
사용한다. 코드 존재, 알려진 결함, 예정 작업, 설계 필요 범위를 구분한다.
이 문서로 사용자 QA를 통과 처리하지 않는다.

각 흐름을 전달할 때:

1. 의미 있는 공통 fixture로 공통 정책·digest 계약을 검사한다.
2. 어댑터 변환과 실제 권한·증적 경계를 검사한다.
3. 해당 클라이언트 구현으로 영향받는 공유 Page를 확인한다.
4. 필요한 경우 승인된 실제 플랫폼 증거를 별도로 기록한다.
5. Main·공통 계약 변경 시 영향받는 기존 Lite 동작을 재검증한다.

이는 위험 기반 증거 계층이다. 요구사항마다 하나의 테스트나 에디션마다 모든
테스트를 복제하라는 뜻이 아니다. fixture 기반 Main UI는 조합을 보여줄 뿐 실제
서버 연동을 증명하지 않는다.

#230은 누적 증거를 종합하며 정합성 검증을 전체 Main 완료 후로 미루지 않는다.
#231은 실제 GitHub/Jenkins를 먼저, 선정된 세 번째 플랫폼을 나중에 검증한다.
초기 Jenkins 증거는 전체 지원 범위의 수용이 아니다.

## 릴리스 수용

구현 범위, 자동 검사, 사용자 QA, 실제 플랫폼 증거, 원격 CI, 머지를 따로 보고한다.
미구현·미검증 필수 흐름을 정합성 충족으로 표시하지 않는다. 명시적으로 수용한
비차단 잔여에도 영향·담당자·후속 작업을 남긴다.

첫 외부 릴리스의 라이선스, 불변 커넥터, 롤백, 지원 문서는 #193/#196/#68이다.
예정 상태를 이미 보호된 운영 배포물처럼 설명하면 안 된다.
