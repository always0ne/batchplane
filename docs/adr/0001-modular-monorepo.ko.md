# ADR-0001: Main과 Lite를 모듈형 모노레포로 유지

[English](./0001-modular-monorepo.md)

상태: 수용

일자: 2026-08-31

관련 이슈: #191. PR #192/#232에서 2026-10-05 로드맵과 정합화했다.

모노레포 결정은 수용됐다. Main 빌드·계약은 계획 단계이며 기존 Lite 패키지 경계는
이미 분리했다. 이 ADR은 또 다른 리팩터링이나 가상의 공통 패키지를 요구하지 않는다.

## 배경

BatchPlane에는 권한 판단·저장 모델이 다른 두 런타임 에디션이 있다.

- Main은 MySQL을 사용하는 Kotlin/Spring Boot 통제 플랫폼이다.
- Lite는 GitHub 저장소 증적과 GitHub Actions를 사용하는 TypeScript 서버리스 에디션이다.

그럼에도 제품 용어, UI 흐름, 정책·Gate 계약, 사유 코드, 감사 의미, 플랫폼 추상화는
공유한다. 이 경계는 Lite 우선 리팩터링에서 분리했으며 Main과 첫 공통 GitHub
Actions 플랫폼 구현 과정에서 함께 발전시킬 수 있다.

지금 저장소를 나누면 계약이 안정되기 전에 버전별 패키지 배포와 저장소 간 변경
조율이 필요해진다. 반대로 코드를 구분 없이 하나의 빌드에 묶으면 Main/Lite 구현
상세가 직접 결합되는 문제가 생긴다.

## 결정

현재 제품 단계에서는 하나의 기준 소스 저장소를 모듈형 모노레포로 사용한다.

이는 소스 관리 결정이지 실행 파일·빌드·배포물·릴리스 버전을 하나로 만들겠다는
결정이 아니다. Main, Lite, 공통 라이브러리, 정책 코드와 플랫폼 번들은 독립적으로
빌드하고 릴리스할 수 있어야 한다.

허용하는 의존 방향:

```text
Main ----\
          +---> 공통 UI, 계약, 정책, 플랫폼 SPI
Lite ----/

Main --X--> Lite 구현
Lite --X--> Main 구현
```

필수 규칙:

1. Main과 Lite는 상대 에디션의 구현 패키지를 가져오지 않는다.
2. 공통 모듈에는 제품 계약이나 실제 공통 동작을 둔다. 에디션별 전송·저장·신원·
   플랫폼 payload 타입을 넣지 않는다.
3. Main과 Lite는 각자 조합 진입점, 빌드 진입점, 런타임 테스트, 배포 파이프라인,
   릴리스 배포물을 갖는다.
4. React 제품 Page 소스와 적용 가능한 동작 테스트는 공유하되 Main/Lite가 각각
   배포 가능한 UI 빌드를 만든다.
5. 루트 CI는 에디션 간 계약·정합성 테스트를 실행한다. 경로별 job으로 무관한 빌드를
   생략할 수 있지만 공통 모듈 변경 시 모든 영향 사용부를 검사한다.
6. 독립 배포 단위는 다른 에디션의 애플리케이션 구현 없이 빌드·테스트할 수 있어야 한다.
7. 공개 계약과 배포물은 버전 관리해 향후 저장소 분리 시 의존 경계를 재설계하지 않도록 한다.

TypeScript에는 pnpm workspace, Kotlin에는 Gradle multi-project 또는 composite
build를 사용할 수 있다. 루트 빌드는 두 빌드 시스템을 조율할 뿐 한 도구가 다른
도구 체인을 소유하지 않는다.

## 릴리스와 배포

소스가 같은 저장소에 있어도 Main·Lite·Gate Action·플랫폼 번들·공통 계약은
각자 배포물 버전과 릴리스 주기를 사용할 수 있다.

나중에 작은 배포 전용 저장소를 만드는 것도 금지하지 않는다. 예를 들어 컴파일된
GitHub Action을 릴리스 전용 저장소에 복제해 소비자의 다운로드 크기를 줄이거나
게시 자격 증명을 격리할 수 있다. 후속 ADR이 바꾸기 전까지 모노레포가 기준
소스 저장소다.

## 재검토 시점

아래 두 조건을 모두 만족한 뒤 저장소 분리를 검토한다.

- Main이 공유 UI와 정책/Gate 계약으로 운영 가능한 수직 흐름을 완성한다.
- 두 호스팅 방식에서 GitHub Actions가 동일 플랫폼 및 Main/Lite 정합성 검사에 통과한다.

그때 다음 조건 중 하나 이상이 있으면 분리 근거가 될 수 있다.

- Main/Lite의 유지보수 팀과 소유 경계가 독립적이다.
- 릴리스 주기와 지원 기간이 크게 다르다.
- Action 게시와 Main 릴리스 자격 증명에 저장소 수준 보안 격리가 필요하다.
- 대부분 변경이 더 이상 공통 계약이나 에디션 간 검증에 영향을 주지 않는다.
- 저장소 크기·CI 시간이 독립 개발을 느리게 한다는 측정 근거가 있다.
- 비공개·접근 제한 모듈에 별도 접근 경계가 필요하다.
- 플랫폼 연동이 독립 유지보수자와 릴리스 생태계를 갖는다.

이 조건들은 재검토 계기이며 자동 분리 조건이 아니다. 분리하려면 새 ADR에서
안정된 버전 계약, 이전 순서, 릴리스 소유권, 저장소 간 정합성 CI를 정의해야 한다.

## 결과

장점:

- 정책·Gate·UI·계약 변경을 하나의 단위로 검토·검증할 수 있다.
- Main을 점진 도입하는 동안 Lite를 계속 실행할 수 있다.
- PR 하나에서 에디션 간 동등한 동작을 증명할 수 있다.
- 성급한 패키지 게시와 저장소 간 머지 조율을 피한다.
- 모듈 경계를 강제하면 이후 실용적인 분리 경로가 남는다.

비용과 위험:

- 루트 CI와 릴리스 자동화가 복잡해진다.
- 경로 필터·의존 검사·코드 소유권으로 무관한 변경이 묵시적으로 하나의 릴리스에
  묶이지 않도록 해야 한다.
- 금지 의존성과 정합성 위반이 빌드 실패로 이어지지 않으면 모노레포가 아키텍처
  결합을 숨길 수 있다.
- GitHub Action 배포에는 나중에 더 작은 릴리스 범위가 필요할 수 있다.

실제 런타임과 영향 사용부가 생길 때 빌드/CI 통제를 도입한다. 문서 전달만으로
두 도구 체인을 돌리지 않는다. 빈 모듈, 별도 UI kit, 미사용 계약 게시를 이 ADR이
승인하는 것은 아니다.
