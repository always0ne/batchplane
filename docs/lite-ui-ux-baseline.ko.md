# Lite UI/UX 기준

[English](./lite-ui-ux-baseline.md)

## 플랫폼 입력 경계

업무 메타데이터와 플랫폼 실행 설정을 분리해도 배치 등록·변경은 Page 하나, 작성
흐름 하나, 미리보기 하나, 변경 요청 하나로 유지해야 한다. 플랫폼 입력 컴포넌트는
두 번째 설정 wizard가 아니다. 기존 명령·runner/사용자 label·파일·형상·스케줄
컨트롤을 유지하고 상세·실행 요청에서도 어디서 무엇을 수행할지 보여준다. 공유
화면은 GitHub Actions만 있다고 가정하거나 workflow/YAML을 직접 해석하지 않는다.
범용 JSON 폼 엔진 대신 이름 있는 React 컴포넌트와 타입 props를 사용한다. 시각
재설계를 뜻하지 않는다.

가장 최근 선택한 실행 파일이 미리보기·제출 업로드의 기준이다. 읽는 중·읽기 실패에는
낡은 통제 파일 미리보기를 숨기고 제출 핸들러까지 차단하며 번역된 비활성 사유를
제공한다. 유효 재선택 성공까지 기존 작은 오류 영역에 읽기 오류를 유지하고 제출로
지우지 않는다. 업로드 없는 경로·기존 파일 메타데이터도 보존한다. 작성·복구 화면을
떠나거나 대상/클라이언트를 바꾸면 늦은 결과·오류로 현재 화면에서 이동하지 않는다.
현재 작업의 완료는 내부 요청 상세를 연다. 늦은 결과를 무시한다고 서버 요청이
취소되지는 않는다.

이 문서는 Lite 화면의 UI/UX 기준이다. 모든 화면 PR은 검토 전에 범위와 대조하는
것이 원칙이다. `control-plane-srs.ko.md`, `main-lite-conformance.ko.md`의 공통
제품 모델을 구체화한다. Page·탐색 개념·주요 동작은 공유 Main/Lite React에 적합해야
한다. GitHub 전용 컨트롤은 연결·플랫폼 상세·원본 링크 영역에 둔다.

## 제품 탐색

- 실행내역·특정 실행·실패는 `/executions`, `/executions/:executionId`,
  `/executions/failures`, 설정은 `/workspace`다.
- 제품 탐색에는 실행내역·요청·감사(Executions, Requests, audit)를 쓰며 플랫폼 Run·
  Governance 분류를 쓰지 않는다. 원본 링크는 실제 플랫폼명을 유지해 외부 목적지를 숨기지 않는다.
- 실패는 실행 조회에 속하며 탐색 상태에서 전체 목록과 구분한다. 직접 접근·필터·
  정확한 스케줄 회차/attempt 링크·후속처리·로그 접근을 유지한다.
- 현재 내처리함 목적과 변경·실행 요청 작성/상세 경로를 보존한다. 두 번째 작성 흐름을
  만들거나 통합 요청서가 제공되는 것처럼 표현하지 않는다.
- [통합 요청](./unified-request-feature-spec.ko.md)은 별도 유예 기능이다. 리팩터링
  이후 구현 전에 전체 작성·승인·항목 처리 UX를 검토한다.

## 운영자 흐름

Lite는 하나의 연결된 운영 흐름으로 읽혀야 한다.

1. GitHub 저장소 기반 Workspace 연결.
2. 설정 요청으로 Lite 설치.
3. 정의·생성 workflow·선택 파일을 포함한 변경 요청으로 배치 등록.
4. 승인함에서 등록 변경을 검토·결정.
5. 활성 Gate 보호 배치의 실행 요청.
6. 실행 맥락을 검토하고 승인·반려.
7. dispatcher가 통제 workflow를 호출.
8. 실행 증거·Gate 결정·실패·감사 이력 검토.

스케줄은 승인된 배치 변경이 무인 회차를 허용한다. native Run은 회차별 사람 승인·
dispatcher 전달 없이 같은 workflow에서 요청·Gate·결과를 기록한다. 상세에는
승인 누락이 아니라 스케줄·원본 통제 형상 근거를 보여주고 정확한 회차/attempt로
연결한다. [스케줄 계약](./schedule-execution-contract.ko.md)을 참조한다.

## 화면 책임

- Workspace는 현재 제품 정책과 주입된 GitHub 연결·설치 준비 상태를 보여준다.
  Main 소속 관리는 #227/#228 예정이며 현재 Lite 컨트롤이 아니다. 정책과 연결
  상세를 구분한다. 생성 workflow가 현재 템플릿보다 낡았으면 경로·업데이트 PR을 제공한다.
- 등록은 통제 대상, 수행 내용·위치, 변경할 통제 파일을 보여준다.
- 승인함은 아직 승인·반려할 수 있는 작업만 보여준다. 스케줄 회차는 Gate·결과가
  아직 없어도 수동 승인 작업·건수가 되지 않는다.
- 등록·변경 상세는 내부 결정 전에 상태·외부 메타데이터·통제 점검·YAML 변경 요약을
  보여준다.
- 실행 요청 상세는 상태·요청자·배치 맥락·workflow/ref·runner·명령·digest·정규
  payload·승인·dispatcher·Gate 증거라는 전체 판단 기록을 보여준다.
- 배치 목록은 운영 목록이며 향후 최근 실행·대기 요청 건수·실패 신호를 포함하는
  것이 바람직하다.
- 배치 상세는 한 배치의 운영 화면이다. 통제 상태·실행 대상·요청 동작·최근 증거를
  보여준다. 삭제 요청으로 활성 정의가 사라져도 같은 경로에서 not-found가 아닌
  삭제 형상을 보여주고 감사용 최근 실행 접근을 유지한다.
- 목록·상세는 어댑터가 제공한 형상 통제 상태를 사용한다. `BYPASSED`, `UNKNOWN`은
  수동 실행 불가이며 버튼에 간단한 사유를 둔다. 상세는 어댑터가 허용한 복구 동작만
  표시하고 생성 요청의 내부 상세로 이동한다. 생성만으로 자동 해제하지 않는다.
- 실패·실행 상세·내처리함·감사는 승인 후 후속 화면이며 승인함에 합치지 않는다.
- 내처리함은 현재 사용자 작업함이다. 승인 작업·자기 등록/실행 요청·실패 후속처리를
  간결하게 묶고 관련 내부 상세로 연결한다. 유효 소명이 없는 업무 실패는 수동
  요청자 또는 실행된 스케줄 형상의 배치 담당자에게 `Write follow-up`을 준다.
  소명 없는 Gate 차단은 업무가 실행되지 않았으므로 `Gate blocked` 증거 작업과
  `Review evidence`다. `AWAITING_REVIEW`는 적격 관리자만의 검토이고 `APPROVED`는
  작성자·요청자 작업을 해제한다. `CHANGES_REQUESTED`, `REJECTED`는 작성자·담당자의
  `Submit follow-up update`다. 배정된 `OPEN`, `INVESTIGATING`은
  `Continue follow-up`일 수 있지만 같은 사용자·기록에 모순된 중복 검토를 주지 않는다.
  Gate 차단 보완·진행 건은 Gate label·맥락을 유지한다.
- 감사는 증거 타임라인이다. 이벤트 유형·행위자·시각·원본 링크·간단한 메타데이터와
  배치 ID·요청 ID 필터를 제공하는 것이 원칙이다.
- 실행 목록에는 수동·native 스케줄을 포함한다. 하나의 플랫폼 Run에 여러 스케줄이
  있어도 상세·로그 링크와 attempt 결과를 구분하며 실패를 다른 스케줄로 복사하지
  않는다. 주 이력 화면이므로 실패 전용 바로가기 전에 정상·진행 중·업무 실패·Gate
  차단을 보여야 한다.
- 실패 목록·바로가기는 후속 실행 증거만 보여준다. Gate·업무 실패를 구분하고 실행
  상세로 연결한다. 업무 실패 소명은 내용·조치·담당자·상태·작성자·시각·관련 증거를
  기록해야 한다. 관리자 결정 전에는 운영자 소명이 최종 종결인 것처럼 표시하지 않는다.
  운영 상태(`OPEN`, `INVESTIGATING`, `RESOLVED`, `ACCEPTED_RISK`)와 검토 상태
  (`AWAITING_REVIEW`, `APPROVED`, `CHANGES_REQUESTED`, `REJECTED`)를 따로 보여준다.
  제품 클라이언트가 적격으로 판정한 사용자만 검토 컨트롤을 본다. 불가는 큰 설명
  패널이 아닌 간단한 사유·tooltip을 쓴다. 소명·검토 시각은 현재 locale의 간결한
  형식이며 비거나 잘못된 값은 번역된 알 수 없음으로 표시한다. 승인·보완·반려에는
  사유가 필수다.
- Lite는 소명의 `requestId`, `batchId`가 해당 요청과 일치할 때만 수용하고 중복
  `followUpId`에서는 최초 유효 원본 댓글을 보존한다. 실제 GitHub 작성자·시각과
  현재 `admin`/`maintain` 검증을 사용한다. 기본 `SELF_APPROVAL_BLOCKED`는 명시적
  정책 허용 없이는 작성자 자가검토를 막는다. `SELF_APPROVAL_ALLOWED`, `AUTO_APPROVE`는
  적격 관리자의 수동 자가검토를 허용하지만 자동 모드도 명시적 댓글·공백 아닌 사유
  없이 실패 후 결정을 만들어내지 않는다. 댓글은 편집·삭제될 수 있고 클라이언트 간
  트랜잭션 잠금도 없으므로 불변 증거라고 표현하지 않는다.
- 실행 상세는 통제 증거와 업무를 분리한다. Gate 차단은 명령 미수행, 업무 실패는
  Gate 허용 후 실패로 설명한다. GitHub 링크·job 결과 요약·Gate와 업무 job의 native
  로그 접근을 제공한다. 인라인 로그는 필요 시 조회·검색·표시량 제한·다운로드가
  가능하며 영속 저장하지 않은 원시 텍스트임을 명확히 한다. 기본은 배치 명령 group,
  준비·checkout 증거가 필요하면 전체보기를 제공하는 것이 원칙이다.

## 조회 연속성

실행·실패·감사·대시보드는 제품 클라이언트 결과를 사용한다. 연결과 증적 해석은
어댑터 책임이며 새 사용자 단계·화면 모드가 아니다.

- 대시보드 실패·승인 건수는 대상 목록과 같은 적격 기록을 센다. Gate 불명은 검증된
  업무 실패가 아니며 native 회차는 사람 승인 작업이 아니다.
- 새로고침은 새 조회다. 실패를 성공한 빈 결과와 구분하고 임의 빈 목록으로 감추지 않는다.
- 언어 변경은 경로·필터·로그 보기/검색·미제출 소명을 보존한다. 표현만 바꾸며 조회
  실행을 바꾸지 않는다.
- 실행·Workspace 전환 시 대기 작업을 격리한다. 늦은 조회·로그·소명 완료가 새
  화면을 바꾸거나 미확인 결정을 성공처럼 보이면 안 된다.
- 내부 목적지는 원본만 있는 기록·삭제 배치 이력까지 정확한 회차·attempt를 유지한다.
  외부 링크는 보조 증거이며 제공 가능한 제품 상세의 대체가 아니다.
- 로그 원문·다운로드를 유지한다. 모바일에서도 업무/전체 선택·검색이 페이지 폭을
  넓히지 않고 동작해야 한다.

이는 기존 실행 후 기능을 보존하는 검사다. 결과 동기화·실제 취소·백필·새 검토
정책·더 강한 보존을 구현한다는 뜻이 아니다.

## 승인 UX 규칙

- 승인 전에 배치 ID·요청 ID, 요청자·만료, 사유, workflow 경로/ref, runner label,
  배치 명령, Gate 필수 상태를 판단 맥락으로 보여야 한다.
- digest는 보이는 감사 증거이며 주요 판단 자료가 아니다.
- 스케줄 권한·Gate·업무 결과는 다른 사실이다. 승인·dispatcher 빈칸으로 사람의
  작업이 필요해 보이면 안 된다. 모르는 예정 시각·결과를 관찰 시각·가짜 성공·
  잘못된 업무 실패로 채우지 않는다.
- 실패·Gate 차단·전달 중·전달 완료·반려 Issue에 승인/반려 컨트롤을 주지 않는다.
- 실행 반려에는 사유가 필요하다.
- 현재 정책이 적격 자가승인을 허용하는 `SELF_APPROVAL_ALLOWED` 또는
  `AUTO_APPROVE`가 아니라면 명시적 사유와 함께 자가승인을 비활성화한다.

## Workspace 설정 UX 규칙

- 메뉴명은 Repo Settings가 아니라 Workspace 용어를 쓴다.
- GitHub owner/repository는 Workspace 내부 연결 상세이지 제품 설정 개념이 아니다.
- Lite 연결 폼이 자격 증명을 소유한다. 공유 설정은 플랫폼 입력·산출물을 직접
  요구·해석하지 않고 연결 결과·설치 준비·정책을 표시한다.
- 저장은 검증이 아니고 설치/업데이트·정책 요청은 적용이 아니다. 현재·요청 정책과
  반환된 원본 요청 링크를 구분해 표시한다.
- 같은 화면의 연결 확인이 현재 값을 저장·검증한다. 설치/업데이트·정책 요청은
  연결 필드를 저장하지 않는다. 편집·명시적 저장·해제·확인 실패는 이전 검증·요청
  결과를 무효화한다. 불가 동작에 간단한 번역 사유를 주며 낡은 응답이 재활성화하지
  못한다. 확인을 위해 필수 추가 화면·wizard 단계를 만들지 않는다.
- 자격 증명 입력과 저장 세션 요약을 함께 둔다. 정책은 연결 설치 상태와 다른
  책임이다. 단일 Lite 편집기로 미래 Workspace도 플랫폼 하나만 가능하다고 암시하지
  않는다. 연결 목록·공유·이관은 별도 범위다.
- 저장·확인·해제·미설치/부분 설치·최신 설치·업데이트·정책 요청을 영어/한국어,
  데스크톱/모바일에서 확인한다. 이전 연결의 늦은 결과가 새 상태를 대체하면 안 된다.
- 승인 모드 변경은 `.batch-governance/workspace.yml` PR을 만들며 브라우저 로컬
  정책으로 저장하지 않는다.
- 생성 workflow 업데이트는 Workspace에서 PR로 요청한다. 기본 브랜치 직접 쓰기나
  저장소 소유 정책 파일을 템플릿 불일치로 표현하는 것은 금지한다.
- `AUTO_APPROVE`는 수동 실행·변경 요청에 명시적인 Workspace 정책 승인 증적을
  부여함을 설명한다. UI 직접 전달은 여전히 금지다. 자가승인도 포함함을 설명한다.
  스케줄 회차는 승인 스케줄 형상으로 인가하므로 모드 영향을 받지 않는다.

## Gate UX 규칙

- Lite 배치에 Gate는 필수다.
- 선택 기능·토글로 표시하지 않는다.
- 문구는 보호하는 동작 가까이에 간결하게 둔다.
- 미준수 기록도 증거로 볼 수 있지만 실행 요청할 수는 없다.

## GitHub 위임 UX 규칙

- 변경 요청·실행 Issue 생성 후 반환된 내부 상세로 즉시 이동하는 것이 원칙이다.
  변경의 브랜치·파일·PR 처리는 Lite 어댑터가 맡는다.
- 생성 직후 Issue·PR·Actions 표시가 잠시 지연될 수 있음을 알리는 것이 원칙이다.
- 브라우저가 직접 통제 workflow를 전달한다고 암시하지 않는다. 승인 뒤 저장소
  dispatcher가 전달한다.
- 전달 뒤 Actions 표시도 지연될 수 있다. 연결 증거가 생기면 실행 상세 링크를
  제공하고 아직 보이지 않는 실행을 승인 실패 증거로 표현하지 않는다.
