# BatchPlane 사용자 QA 시트

[English](./user-qa.md)

기준일: 2026-10-05. 기준 main: `35eb868396d85e80a1a7c81297e59a3a19e9ffb8`.
이 문서는 #232 전달물이며 **제품이 검증됐다는 보고서가 아니다**.
아래 27개 사례의 사용자 검증 결과는 모두 `NOT_TESTED`로 시작한다.
이후 버전의 결과는 [결과 기록 양식](./qa-result-template.ko.md)에 별도로 기록한다.

## 사용 기준

기능별 무제한 조합이 아닌 실제 업무 흐름 단위로 확인한다. 공통 절차를
Main/Jenkins에서 반복할 때는 기존 사례 ID와 환경을 기록하며 사례를 복제하지 않는다.
자동 테스트 개수나 이 문서의 사례 수는 품질 목표가 아니다.

| 구현 준비 상태    | 뜻                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------- |
| `AVAILABLE`       | 관련 기능이 있으므로 사용자 확인 가능. 통과했다는 뜻은 아님.                          |
| `KNOWN_GAP`       | 현재 구현에 알려진 보정 사항이 있음. 일부 확인은 가능하나 전체 통과로 기록할 수 없음. |
| `PLANNED`         | 확정된 후속 기능. 아직 없는 버튼을 찾거나 작동하는 것으로 가정하지 않음.              |
| `DESIGN_REQUIRED` | 상세 모델/UX/연동 계약 승인 후에 실행 절차를 확정해야 함.                             |

결과는 `NOT_TESTED / PASS / FAIL / BLOCKED / RETEST_REQUIRED / N/A` 중 하나로 기록한다.
`N/A`에는 에디션/지원 범위 근거가 필요하다. 미구현을 `N/A`로 숨기지 않는다.
`BLOCKED`와 `FAIL`은 원인·관련 이슈를 연결한다. 변경으로 이전 PASS의 유효성이
달라졌다면 새 회차에 `RETEST_REQUIRED`를 남기며 이전 결과를 덮어쓰지 않는다.
구현 준비 상태와 결과는 다른 열이다.

## 안전한 준비

- 운영 배치가 아닌 사용자가 승인한 테스트 Workspace와 저장소를 사용한다.
  실제 GitHub 쓰기·실행·취소는 실행 시 별도 승인받은 환경에서만 수행한다.
- 일반 요청자 A, 승인 가능한 사용자 B, 권한 없는 사용자 C를 준비한다.
  관리자 검토는 해당 권한 보유자가 수행한다. 한 계정만 있으면 자가승인 허용
  확인은 가능하지만 권한 분리·무권한 차단 검증을 통과로 처리하지 않는다.
- 성공 명령은 `printf 'QA_OK\n'`, 업무 실패는 `exit 7`, 중단 시험은
  `sleep 120`처럼 외부 업무 효과가 없는 명령으로 준비한다. 취소는 롤백이 아니다.
- 배치 ID는 `qa-success`, `qa-failure`, `qa-cancel` 등으로 구별한다.
  실제 실행되지 않은 샘플은 증거가 아니다. 파라미터 계약 #212와 취소 #225는
  구현 후 확정된 입력/화면 절차를 이 시트에 반영한다.
- 앱의 commit/build, Action SHA, 대상 저장소/default branch, Workspace 정책,
  사용자 역할, 브라우저/locale/viewport를 기록한다. 토큰과 민감 로그는 남기지 않는다.
- UI 관찰, 자동 테스트 결과, 실제 GitHub 실행/댓글/PR 증거를 구분한다.
  mock 결과로 #202를 통과시키거나 원격 CI 성공을 사용자 QA로 대신하지 않는다.

## Lite 핵심 흐름

### QA-L01: 연결 확인과 설치 상태가 실제 저장소 상태를 따른다

준비 상태: `AVAILABLE`. 연결/설치/업데이트, sessionStorage.

절차: Workspace에서 전용 저장소와 토큰을 입력하고 연결 확인한다. 미설치이면
설치 요청을 만들고 반환된 상세로 이동한다. 사용자 승인·반영 뒤 다시 확인한다.
오래된 관리 파일이 있는 시험 환경에서는 업데이트 요청의 변경 범위를 확인한다.
그 다음 입력값을 바꾸거나 연결을 끊어 이전 확인 결과와 진행 중 결과가 재사용되지 않는지 본다.

기대: 연결 저장, 연결 검증, 설치 요청, 실제 적용 상태가 구별된다. 미검증 연결로
설치/정책 명령을 수행할 수 없고 이유가 보인다. 토큰은 localStorage에 남지 않으며
연결 제거 후 UI/저장소에 복원되지 않는다. 테스트 증거에 토큰을 포함하지 않는다.

### QA-L02: 등록 요청의 내용이 승인 후 배치와 실행 파일에 반영된다

준비 상태: `AVAILABLE`. 승인 권한 일치의 남은 사항은 QA-L05로 함께 확인.

절차: A가 고유 ID, 이름, 환경, `runs-on`, 배치 명령을 입력한다. 파일 실행을
시험할 때만 안전한 파일을 첨부한다. 담당자 빈 값과 명시한 값을 각각 필요한
경로에서 확인하고 미리보기 후 요청한다. 상세에서 B가 내용을 확인하고 승인한다.

기대: 요청 생성 직후 내부 상세로 이동한다. 승인 전 적용되지 않고, 승인된 명령,
런타임/파일과 `{batchId}.yml` 경로가 적용된다. Gate는 항상 필수다. 빈 담당자는
미리보기·digest 계산 전에 실제 요청자로 채워지며 명시한 담당자는 보존된다.
상세에서 해당 배치로 이동할 수 있다. PR 링크는 보조 증거다.

### QA-L03: 변경·스케줄 추가/수정/삭제는 한 변경 요청과 실제 diff에 담긴다

준비 상태: `AVAILABLE`, cron 일치 보정은 QA-L16의 `KNOWN_GAP` 포함.

절차: 기존 배치에서 변경 요청을 연다. 현재 값이 채워졌는지 확인한 뒤 명령과
스케줄을 변경하고 다른 스케줄을 삭제한다. 미리보기와 요청 상세에서 이전/제안
값을 비교한다. 승인 전 원본, 승인 후 적용 결과를 각각 확인한다.

기대: 빈 등록 화면으로 가지 않는다. 실제로 바뀐 필드와 제거된 스케줄이 diff에
보이고 단순 ‘변경 없음’으로 표시되지 않는다. 상세 화면에서 직접 스케줄을
저장하지 않는다. 미리보기의 삭제는 요청 반영 대상이며 승인 전 원본 삭제가 아니다.
요청 내용이 바뀌면 이전 승인을 새 내용에 재사용하지 못한다.

### QA-L04: 배치를 삭제해도 과거 형상과 실행·소명에 접근한다

준비 상태: `AVAILABLE`.

절차: 실행 및 실패 소명 이력이 있는 시험 배치에 삭제 요청을 제출한다. 승인
전후를 확인하고, 삭제 후 기존 실행 링크·감사 링크·과거 배치 링크로 접근한다.

기대: 삭제는 승인 후 반영된다. 실행 당시 명령/스케줄 등 보존 형상과 원래
요청/소명에 접근한다. 삭제된 배치를 신규 실행 가능 상태로 표시하지 않는다.
GitHub 원본 보존 기한이나 권한 때문에 자료가 없으면 ‘기록 없음’과 구별한다.

### QA-L05: 승인 화면·실제 승인 명령·Gate의 권한 판단이 일치한다

준비 상태: #223/BF-7 보정 후 `AVAILABLE`. 버전별 결과를 기록하기 전까지
사용자·실제 플랫폼 QA는 NOT_TESTED다.

절차: A 요청을 A/B/C 각각의 실제 역할로 조회한다. 유효 정책을 자가승인 금지,
허용, 자동승인으로 변경·적용한 뒤 영향받는 대표 흐름을 확인한다. 무권한 사용자의
차단과 실제 승인 가능한 사용자 경로를 함께 본다. 준비된 이력 fixture 또는 전용
환경에서 100건 이후에 있는 승인 근거도 조회·검증한다. 매번 100건을 수동 생성하지 않는다.

승인함과 요청 상세에서 부적격 사용자와 권한 조회 실패의 승인·반려 비활성화 사유가
구별되는지 확인한다. 요청 내용은 계속 읽을 수 있어야 한다. 역할 매핑 누락, 낡은
draft 모드, 불일치·편집 댓글, 후속 페이지 실패는 결정적인 fixture로 확인하며
그 상황을 재현하기 위해 실제 운영 저장소를 임의 변경하지 않는다.

기대: 완화 모드도 없는 승인 권한을 만들지 않는다. 금지 모드는 자가승인을 막고,
허용/자동 모드의 적격 자가승인은 가능하다. 자동승인은 별도 정책 증거를 남긴다.
버튼, 명령, Gate가 같은 결론을 내며 첫 페이지 밖의 유효 승인도 찾는다.
보정한 버전에서 이 흐름을 재검증한다. 자동 검사 통과로 사용자 QA 통과를
이어받지 않는다.

기대 증거: 뒷페이지의 결정을 확인하며 나중의 유효 반려도 누락하지 않는다. 불완전한
이력은 부재가 아닌 조회 불가로 남긴다. 실제 댓글 작성자와 대상 digest로 결정을
식별한다. 자동 fixture 결과·브라우저 확인·사용자/플랫폼 QA를 버전별로 별도 기록한다.

### QA-L06: 승인된 파라미터가 실제 업무 명령의 입력이 된다

준비 상태: `KNOWN_GAP` #212.

절차: #212에서 승인할 입력 계약으로 비밀이 아닌 `qa-value-1`을 받는 시험 배치를
준비한다. 미리보기/요청/승인 내용과 실제 업무 출력을 비교한다. 승인 이후 다른
값으로 실행하려는 사례도 해당 계약의 검증 경로에서 확인한다.

기대: UI 요청 기록이나 dispatch 성공만이 아니라 실제 명령이 승인된 값을 쓴다.
승인되지 않은 값은 실행되지 않는다. 민감 입력은 원문 기록을 만들지 않는다.
자동승인 모드에서도 최신 요청 상태가 보이며 연계된 **실행 상세**로 이동한다.

### QA-L07: 실제 native 스케줄이 승인 형상으로 실행되고 결과가 연결된다

준비 상태: `AVAILABLE`, 실제 GitHub 증거는 #202 대기.

절차: 전용 저장소에서 Batch 변경 요청으로 가까운 미래의 cron과 IANA timezone을
등록·승인한다. 원본 workflow/default branch와 설정된 지역 시각을 기록한다.
수동 버튼 대신 실제 `schedule` 이벤트를 기다린다. 발생한 occurrence의 요청,
원래 변경 승인, Gate, 업무 job 및 결과를 확인한다. 여러 스케줄이 있는 경우
한 스케줄 실패가 다른 스케줄 결과에 복사되지 않는지도 전용 사례로 확인한다.

기대: 매 회차 사람 승인/자동승인 댓글이나 두 번째 dispatcher 실행 없이 같은
native 실행에서 처리된다. `repositoryId/batchId/scheduleId/sourceRunId`와 실제
attempt/job이 일치한다. 업무는 검증된 SHA로 실행된다. 지연·미발생은 사실대로
기록하고 수동 실행을 cron 검증으로 대체하지 않는다. worker 시각을 예정 시각으로
추정하지 않는다. 자세한 실환경 조건은 [스케줄 계약](./schedule-execution-contract.ko.md).

### QA-L08: 직접 실행과 full/partial rerun으로 Gate를 우회하지 못한다

준비 상태: `AVAILABLE`, native schedule 실환경 증거는 #202 대기.

절차: 전용 배치에 요청 없는 native 수동 실행, 성공한 수동 실행의 rerun,
스케줄 full rerun과 business-only partial rerun을 각각 지원되는 경로로 시도한다.
별도 허용 요청의 정상 실행도 함께 확인해 무조건 차단을 성공으로 오인하지 않는다.

기대: 재사용/누락 권한으로 업무 명령이 실행되지 않고 차단 사유와 시도가
실행내역에 남는다. 제어 job을 건너뛰어도 업무 진입 검증을 통과하지 못한다.
서로 다른 native Run의 동일 예정 회차를 완전 중복 방지한다고 주장하지 않는다.

### QA-L09: 승인 형상과 다른 배치는 차단되고 정식 변경 요청으로 복구한다

준비 상태: `AVAILABLE`. 테스트 저장소 외 직접 변경 금지.

절차: 승인된 배치의 시험 복제에서 승인 대상 파일을 외부 변경한다. UI의 상태와
요청 가능 여부, Gate 차단을 확인한다. 지원되는 정식 보정/변경 요청을 통해
다시 검토·승인한 뒤 새 실행을 요청한다.

기대: 승인되지 않은 내용은 실행되지 않는다. 복구 과정이 원본 이력을 지우거나
이전 승인을 새 형상에 붙이지 않는다. 탐지/승인 근거를 조회할 수 없는 상황과
정상 상태를 혼동하지 않는다. 이는 관리자 권한으로 시스템 자체를 제거해도
통제가 유지된다는 보장이 아니다.

### QA-L10: 만료·전달 실패는 종결되고 새 요청을 만들 수 있다

준비 상태: `PLANNED` #224. 기존 retry-dispatch는 현재의 알려진 정책 차이.

절차: 상세 설계/구현 후 전용 fixture로 만료와 **확인된** 전달 거절을 만든다.
요청 상세와 다음 변경/실행 요청 가능 여부를 확인한다. 다음에는 승인 여부를
알 수 없는 전달 응답을 별도 사례로 확인한다.

기대: 만료/실패가 다음 유효 작업을 영구 차단하지 않는다. 확인된 전달 실패는
새 요청·현재 정책으로 다시 시작하며 같은 요청 재전달/자동 재실행이 없다.
불확실한 전달은 확인된 실패로 바꾸거나 자동으로 다시 보내지 않는다.

### QA-L11: 철회·대기 취소·실행 중단이 실제 엔진 상태와 맞는다

준비 상태: `DESIGN_REQUIRED` #225. 상세 권한/UX를 승인한 뒤 실제 화면 절차 확정.

절차: 미전달 승인 요청, provider 대기, `sleep 120` 실행 중, 이미 종료한 대상에
대해 승인된 철회/취소 흐름을 확인한다. 요청자·실제 승인자·대상 실행 권한자의
미전달 철회와 무권한 거절을 확인한다. 대기/실행 중에는 사용자 확인·사유와 실제
provider 취소 결과를 기록한다. 완료/불확실 응답의 표시도 확인한다.

기대: 미전달 철회는 전달/Gate에서도 막힌다. 대기는 명시적 취소, 실행 중은
중단 확인을 받는다. 실제 명령 없이 화면만 종료하지 않는다. 이미 끝났으면 실제
결과를 보존하고, 확인 불가면 종료 완료로 만들지 않는다. 취소는 수행된 효과를
되돌리지 않는다. 혼합 대상의 일부 실행을 숨긴 전체 철회 표시도 금지한다.

### QA-L12: 실행 상세와 업무/전체 로그가 정확한 대상에 연결된다

준비 상태: `AVAILABLE`.

절차: 정상 실행과 `exit 7` 실패, Gate 차단 건을 실행내역에서 연다. 요청 상세,
실패내역, 감사에서 같은 실행으로 이동한다. 기본 로그와 전체 로그를 바꾸고
다른 실행으로 이동하는 동안 이전 로그 응답이 새 화면에 섞이지 않는지 확인한다.

기대: 알 수 있는 배치를 ‘알 수 없는 배치’로 표시하지 않는다. 기본 로그는 실제
배치 명령 구간이고 전체보기는 준비/Gate 등을 포함한다. 차단은 업무 실패와
구별된다. native 전체 결론을 다른 schedule/job/attempt에 복사하지 않는다.
로그 보존 만료·권한 오류는 명시되며 토큰이 앱 로그에 기록되지 않는다.

### QA-L13: 업무 실패 소명은 관리자 검토와 보완을 거쳐 종결된다

준비 상태: `AVAILABLE`.

절차: 업무 실패를 만들고 수동 요청자 또는 실행 당시 스케줄 배치 담당자가
소명/조치 내용을 제출한다. 관리자 검토에서 보완 요청 후 재제출하고 승인한다.
반려 경로는 영향받는 변경 때 추가 확인한다. 허용 정책에서 적격 관리자 자가검토도
확인하되 AUTO_APPROVE로 제출 직후 종결되는 것은 허용하지 않는다.

기대: 제출과 검토 결정/사유가 분리되고 내처리함에서 다음 담당자에게 연결된다.
담당자 지정만으로 권한이 생기지 않는다. 과거 제출/보완/검토가 보존된다.
Gate 차단을 업무 실패로 보아 소명을 억지로 요구하지 않는다.

### QA-L14: 오래된 실행·감사·미처리 업무도 조회 범위에서 사라지지 않는다

준비 상태: `KNOWN_GAP` #226.

절차: 첫 페이지/최근 조회 한도를 넘는 준비된 이력에서 과거 배치를 기간·배치
조건으로 찾는다. 오래된 미처리 소명과 검토를 내처리함에서 연다. 추가 페이지
조회 실패와 provider 원본 접근 불가도 구분해 확인한다.

기대: 최신 일부에만 필터를 적용한 결과를 전체처럼 보이지 않는다. 미처리 항목은
오래되어도 접근 가능하다. 일부 조회와 오류를 ‘없음/완료’로 만들지 않는다.
무제한 로딩/새 캐시를 구현했다는 조건은 없다. 원본 보존 한계와 제품 누락을 구별한다.

### QA-L15: 요청 생성·승인 뒤 내부 상세와 목록이 최신 결과를 보여준다

준비 상태: `AVAILABLE`.

절차: 등록/변경/실행 요청을 한 건씩 만들고 반환 상세, 승인함/요청 목록,
새로고침 상태를 확인한다. 자동승인 요청에서도 승인 상태 및 연계 실행 상세를
확인한다. 선행 처리 중인 요청으로 차단되면 해당 내부 상세로 이동한다.

기대: 사용자가 GitHub에서 작업을 이어야만 하는 동선이 아니다. 성공 응답 뒤
이전 상태를 보여 중복 승인하도록 하지 않는다. native 실행 발견이 아직 안 됐으면
확인 중이라는 사실을 보여주고 실패/완료를 추정하지 않는다. 초 단위 응답 보장은
별도 합의 없이 만들지 않으며 재현 시 요청/응답 시각을 근거로 기록한다.

### QA-L16: 배치 간 스케줄 현황과 입력·미리보기·생성이 일치한다

준비 상태: `PLANNED` #206, cron 일치 BF-3는 알려진 보정 대상.

절차: 여러 배치의 활성/비활성 스케줄을 현황에서 찾고 상세→배치→승인 근거→
실행내역으로 이동한다. 지원 cron과 timezone의 다음 시각을 입력 화면/미리보기/
생성 workflow에서 대조한다. 지원하지 않는 형식은 요청 전에 거절되는지 확인한다.

기대: 스케줄 조회를 위해 배치마다 들어갈 필요가 없다. 조회 페이지의 편집은
Batch 변경 요청으로 이어진다. 고정 UTC 변환으로 IANA 의미를 바꾸지 않는다.
예상 시각은 실행 성공 보장이 아니며 지연/미발생과 구별된다.

### QA-L17: 여러 Workspace를 조회하고 공통 승인자로 통합 요청을 승인한다

준비 상태: `DESIGN_REQUIRED` #142.

절차: 승인된 상세 설계 후 서로 다른 Workspace의 여러 Batch/작업 유형을 한
요청에 담는다. 전체 대상 승인 권한이 있는 사용자 유무를 바꿔 생성 가능 여부를
확인한다. 권한 없는 Workspace 조회/항목 추가, 공통 승인자의 전체 승인,
각 항목 결과와 혼합 상태 철회를 확인한다.

기대: 단순 Workspace 전환으로 대체하지 않는다. 공통 승인자가 없으면 생성할
수 없고 있으면 한 사람이 전체를 한 번에 승인한다. Workspace별 승인을 따로
모으지 않는다. 요청 승인과 항목별 수행 결과가 구별되고 권한 밖 데이터는 없다.
Lite 유예는 근거와 사용자 수용을 기록하며 완료로 처리하지 않는다.

### QA-L18: 주요 화면과 다음 행동이 한국어/영어·모바일에서도 읽힌다

준비 상태: `AVAILABLE`. #119는 계속 열린 체크리스트.

절차: 이번 변경의 목록→작성→상세→승인/실행/소명 여정을 영어/한국어,
데스크톱/390px, 키보드로 확인한다. 최초 locale 선택, 언어 변경 중 입력 보존,
loading/error/empty/disabled와 이유 툴팁을 해당 흐름에서 확인한다.

기대: 불필요한 Gate 카드/옵션, 겹침/가로 넘침, 출구 없는 화면이 없다. 핵심 행동은
제품 내부에서 끝나고 source 링크는 보조다. 기술 ID는 번역하지 않으며 언어에
따라 업무 의미/상태가 달라지지 않는다. 영향 없는 모든 화면을 매번 반복하지 않는다.

## Main 및 실제 다중 플랫폼 수용

### QA-M01: Workspace·계정·권한·연결 기본 모델을 먼저 승인한다

준비 상태: `DESIGN_REQUIRED` #227. UI 실행 테스트가 아닌 설계 수용 항목.

절차: 계정/외부 신원/소속/권한, Workspace와 여러 플랫폼 연결, 통합 요청과 공통
승인자, 철회/취소 권한, 식별키 관계 및 MySQL/API 초안을 사용자가 검토한다.

기대: 외부 인증 사실과 제품 인가가 구분되고 Workspace가 플랫폼에 종속되지
않는다. 미승인 모델을 코드로 먼저 고정하지 않는다. 검토 기록/승인 링크를 남기며
그것을 Main 기능 테스트 통과로 표현하지 않는다.

### QA-M02: Main GitHub 첫 운영 흐름을 동일한 UI로 완결한다

준비 상태: `PLANNED` #228, QA-M01 승인과 Lite 수용 이후.

절차: 실제 Kotlin/MySQL와 GitHub 연결에서 QA-L02/L05/L06/L10/L11/L12/L15를
해당 Main 계약으로 수행한다. 요청→승인→입력→Gate→업무→결과/로그/감사를 연결한다.

기대: mock/연결 성공만이 아니라 실제 업무 입력과 취소 결과까지 보인다. UI가
GitHub DTO/토큰에 의존하지 않고 권한은 API와 Gate에서 재확인된다. Main 공급자
비밀값이 브라우저로 반환되지 않는다. 각 사례의 Main 결과를 별도로 기록한다.

### QA-M03: 결과 동기화와 실제 중단은 다른 명령이다

준비 상태: `PLANNED` #228, Main 첫 흐름 필수.

절차: provider에서는 완료됐지만 제품 결과 반영이 누락된 전용 사례에서 결과
동기화를 수행한다. 다른 실제 실행 중인 사례에서 사유 있는 중단을 수행한다.
provider 상태를 확인할 수 없는 경우도 해당 계약에서 확인한다.

기대: 동기화는 확인된 실제 결과를 보정하고 새 실행이나 cancel을 보내지 않는다.
중단은 실제 cancel을 보내고 이미 종료됐으면 해당 결과로 보정한다. 불확실 상태는
성공/실패/취소 완료로 꾸미지 않는다. 두 명령의 주체·사유·결과가 분리된다.

### QA-M04: Main 변경·삭제·실패 검토와 이력 조회를 연결한다

준비 상태: `PLANNED` #228.

절차: Main에서 QA-L03/L04/L13/L14를 수행하고 변경 적용 충돌/실패를 확인한다.

기대: 승인된 변경과 실제 적용 결과가 구별되고 삭제 이력, 소명/관리자 검토,
오래된 미처리 업무가 남는다. GitHub PR 원문을 알아야만 승인할 수 있는 UI가 아니다.

### QA-M05: Main 스케줄 운영과 지연 모니터링이 실제 근거를 따른다

준비 상태: `PLANNED` #229.

절차: QA-L07/L08/L16을 Main에서 수행하고 신뢰할 예정/관찰 시각이 있는 지연과
예정 시각을 모르는 경우를 비교한다. 권한/배치별 현황에서 원래 승인과 결과를 연다.

기대: 승인 형상 기반 무인 실행과 Gate가 유지되고 지연을 모니터링할 수 있다.
모르는 예정 시각을 만들어내거나 놓친 회차를 몰아서 실행하지 않는다.

### QA-P01: 같은 Main Workspace에서 GitHub와 Jenkins를 실제 검증한다

준비 상태: `DESIGN_REQUIRED` #231 A, Main 첫 GitHub 흐름 직후.

절차: 승인된 Jenkins 연동 방식/Job 범위로 두 플랫폼 연결을 한 Workspace에
구성한다. 공통 등록/승인/입력/실행/Gate/결과/로그/동기화/중단을 양쪽에서 수행한다.

기대: 플랫폼별 세부사항은 어댑터에 있고 정책 의미가 같다. 직접 실행/rerun의
실제 Gate 범위도 증명한다. Main 전체 기능 완료까지 검증을 미루지 않는다.
이 결과는 초기 검증이며 Jenkins 정식 지원 전체 완료가 아니다.

### QA-P02: 확장된 Jenkins 범위와 선정한 세 번째 플랫폼을 검증한다

준비 상태: `DESIGN_REQUIRED` #231 B/C.

절차: 승인된 Jenkins 변경/삭제/스케줄/실패 검토 범위에 QA-M04/M05를 적용한다.
별도 선정·승인한 세 번째 플랫폼의 실제 실행/스케줄/통제 차이를 시험한다.

기대: 예시였던 SCDF를 자동 선정하지 않는다. 실제 차이를 근거로 필요한 공통
계약/어댑터만 보정한다. 대상 버전·Job 유형·권한·제약과 증거를 남긴다. 플랫폼
숫자를 채우는 API 연결이나 mock은 수용 증거가 아니다.

### QA-X01: Lite/Main 공통 의미와 의도한 차이를 누적 증거로 수용한다

준비 상태: `PLANNED` #230.

절차: 각 흐름의 Lite/Main 결과를 비교하고 공통 UI/권한/Gate/감사 의미의 차이,
지원 범위와 보존 한계를 기록한다. 변경된 공통 계약에 영향받은 사례만 재검증한다.

기대: 유효한 기존 결과를 재사용하되 버전/환경이 다른 실패를 숨기지 않는다.
GitHub 구현과 MySQL 구현이 별도 제품 정책을 만들지 않는다. 상세 미결정이나
실환경 미검증을 문서 작성만으로 통과시키지 않는다.

### QA-R01: 첫 외부 릴리스의 사용·보안·배포 안내가 실제 지원과 맞는다

준비 상태: `PLANNED` #193/#196/#68.

절차: 릴리스 범위의 라이선스/보안 신고/기여 안내, immutable Action 참조,
보호 설정, 업데이트·rollback 절차와 지원 버전을 실제 배포 산출물에 대조한다.

기대: 개발용 `@main`을 운영 고정 버전으로 표현하지 않는다. 공개 사용을 권장하기
전에 미확정 라이선스를 해소한다. Lite 첫 외부 릴리스에도 적용하며 Main/Jenkins
완료까지 미루지 않는다. 종류·세부 정책은 사용자 결정 없이 확정하지 않는다.
